# 浏览器原理及应用

## 前言

浏览器是一种用于检索并展示万维网信息资源的应用程序，通过了解浏览器可以帮助我们更好地搭建Web应用。这篇博客主要由前端的视角去了解浏览器，同时也会拓展到整个Web应用各环节的一些知识点，但并没有深究前端工作中不大需要了解的知识点，比如模板引擎中解析器和词法分析器的原理等，这些知识点不容易理解和记住，同时在前端工作中用处也不大，感兴趣的话可以参考博客底部的相关链接，里面有比较详细、专业的介绍。
以下内容主要是摘自浏览器厂商（主要是Chrome与Mozilla Firefox，因为目前它们占据着大部分市场份额，也紧密贴合着W3C的标准，同时它们在开源方面也做得更好，所以网上资料也比较多，了解它们的原理对于我们来说已经足够了）官方的文档、更新日志、开发人员博客及论坛中官方开发人员的回复（所以下面的大部分参考链接是需要科学上网才能访问的），还有一些比较好的书籍和个人文章（图也是到处抠来的，自己画是不可能的），这篇博客主要是对这些内容进行了梳理，并结合了一些个人的调研和理解，希望能够帮助自己及他人更全面、系统地了解浏览器。

## 浏览器架构

现代浏览器普遍使用多进程架构，通常浏览器会根据硬件设备的性能来决定如何分配进程，具体实现规则各种浏览器都不一样，详情参阅[这里](https://helgeklein.com/blog/2019/01/modern-multi-process-browser-architecture) 。多进程架构的好处有：

- 更好地利用设备的硬件资源：通过在性能较好的设备上分配更多的进程，提高浏览器的性能与稳定性。在性能较差的设备上分配较少的进程，节省硬件资源的使用。
- 提高浏览器稳定性：通过给不同的服务分配单独的进程，降低浏览器不同服务的耦合，从而提高浏览器的稳定性。例如将多个标签页运行在不同的渲染进程中，可以避免某个标签页无响应导致所有标签页无响应。
- 提高浏览器安全性：浏览器可以沙箱化某些进程，即通过操作系统限制这些进程的权限，从而提高浏览器的安全性，例如Chrome浏览器限制了渲染器进程的文件访问权限。

下面主要以Chrome浏览器的多进程架构做介绍：
![浏览器架构图](https://upload-images.jianshu.io/upload_images/20154859-a49a33b6c9527e6f.png?imageMogr2/auto-orient/strip%7CimageView2/2/w/1240)

Chrome的每个进程都由主线程（浏览器进程中为UI线程，渲染器进程中为Blink线程）、IO线程（用于处理进程间的IPC通信和网络请求）、一些专用线程和通用线程池组成，详情参阅[这里](https://chromium.googlesource.com/chromium/src/+/master/docs/threading_and_tasks.md) 。下面是理想情况下Chrome的进程分配：

- **Browser Process**：浏览器进程，负责各个服务间的协调通信等，它通常包含：
  - Main Thread：UI线程，负责绘制用户界面（如地址栏、前进/后退按钮、书签菜单等），并且接收并反馈用户的操作（如地址栏输入、前进/后退按钮点击等）。
  - IO Thread：IO线程，负责与其它进程的IPC通信和网络请求。
  - Storage Thread：存储线程，负责持久化数据到硬件设备上，如Cookies、Local Storage、Session Storage、IndexedDB、Web SQL等。
  - Device Thread：设备线程，负责管理Chrome设备，可以通过网络注册安装了Chrome应用的设备，然后通过管理中心管理这些设备上的Chrome应用。
- **Utility Process**：用于运行实用程序，它们分别是：
  - Network service Utility：负责处理所有网页、扩展程序以及浏览器自身发起的 HTTP/HTTPS、WebSocket 和 WebTransport 请求，实现和管理各种网络协议，包括 HTTP/1.1、HTTP/2、HTTP/3 (QUIC) 以及 TLS 加密握手，网络缓存（Network Cache），Cookie 与凭证管理，连接池管理（Connection Pooling），DNS 预解析与缓存，流量代理与监控。
  - Audio Service Utility：用于运行音频服务，当在打开音频或者视频时，将会创建此进程，与V8 proxy Resolver一样，它也是从Browser Process剥离出来的，也是为了提高浏览器的稳定性，详情参阅[这里](https://docs.google.com/document/d/1fVHVJjd5zTqc6O7b0lprILyuFPC9qVQUudzjEgOq1HY/edit)。
  - Windows Utilities：Windows系统下的一些实用工具，例如在保存或上传文件时打开Windows文件资源管理器，将创建此进程。
通常会为每个实用程序分配单独的进程。
- **GPU Process进程**：GPU进程，负责处理GPU任务，由于GPU服务需要处理来自多个应用程序的请求并将它们绘制在同一表面上，因此为它分配单独的进程。
- **Plugin Process**：插件进程，负责控制网站使用的插件，如flash等，通常会为每个插件分配单独的进程。
- **Extension Process**：扩展程序进程，负责运行用户添加的浏览器扩展程序，如Vue开发工具、Postman、谷歌翻译等，通常会为每个扩展程序分配单独的进程。
- **Worker Process**：用于运行Shared Worker（共享Worker），它会为每个Shared Worker分配单独的线程，并通过Browser Process连接到多个Renderer Process。需要注意的是，Dedicated Worker（专用Worker）会以单独的线程运行在所属的Renderer Process中，而不是运行在Worker Process中，详情参阅[这里](https://www.chromium.org/blink/web-workers)。
- **Service Worker Process**：用于运行Service Worker，通常会为每个站点注册的Service Worker分配单独的进程。
- **Renderer Process**：渲染器进程，负责渲染页面以展示给用户，Chrome会为每个标签页、每个标签页的DevTool面板和每个跨站iframe（网站隔离：默认启用，为每个跨网站iframe运行单独的渲染器进程），Chrome对可启动的进程数量进行了限制，该限制值取决于设备拥有的内存和CPU能力，当进程数量达到该限制时，它将在一个渲染器进程中运行多个标签页。它通常包含有：
  - Main Thread：Blink线程，它包含一个浏览器引擎，浏览器引擎通常包含一个HTML排版引擎及一个JavaScript解释器，常见的浏览器引擎有：
    - Webkit：Apple公司主导开发的开源项目，用于Apple Safari浏览器，它的HTML排版引擎WebCore与Javascript解释器JavaScriptCore分别Fork自KDE公司开发的开源项目KHTML与KJS。
    - Blink：Google公司主导开发、Opera跟随实施的开源项目，用于Chrome和Opera浏览器，它Fork自Webkit的WebCore组件，并使用了自己的V8 Javascript解释器。
    - Gecko：Mozilla基金会主导开发的开源项目，用于FireFox浏览器。
    - Trident：Microsoft公司开发，用于IE浏览器。由于早期与W3C标准脱节并且未开源，市场占有率一路下跌，近些年基于Chromium开发了Microsoft Edge。
    - 双引擎：国内浏览器通常使用双引擎，使用Trident引擎时称为兼容模式，使用Blink（早期是Webkit）引擎时称为极速模式。**可以通过添加`<meta name="renderer" content="webkit">`声明让浏览器默认使用极速模式**。
  - IO Thread：Browser Process会判断当前渲染器进程是否被授权请求当前URL，如果是普通的http，https和ftp请求，将会由Renderer Process的IO Thread发起网络请求，但Browser Process会阻止Renderer Process请求本地文件系统的URL。当使用浏览器打开本地文件时，会使用专用渲染引擎渲染，详情参阅[这里](http://seclab.stanford.edu/websec/chromium/chromium-security-architecture.pdf)。

Chrome浏览器的多进程架构大致如上，个人认为它走在了浏览器多进程架构的最前沿，所以已它为例子做介绍，FireFox的进程沙箱化也是使用的Chromium的沙箱，通过了解浏览器的架构我们可以更好理解浏览器的不同组成部分是如何协作渲染出Web应用。

## 浏览器的导航流程及渲染原理

“从我们在地址栏中输入URL，到我们在浏览器上看到页面的整个过程中都发生了些什么？”，这是个常见的前端面试问题，通过这个问题可以知道面试者是否了解浏览器的导航流程及渲染原理，而了解它们对于开发Web应用有很大帮助，我们可以针对其中每一步做优化，从而提高Web应用的性能、稳定性等。下面以Chrome浏览器为例详细介绍下每一步：

**1.处理地址栏中的输入内容：**
当用户开始在地址栏中输入内容时，浏览器用户界面（由Browser Process的UI Thread）会判断输入是URL还是搜索查询，如果是搜索查询，则会导航至搜索引擎首页（具体使用的搜索引擎可以在浏览器设置中更改）；如果是URL，则会导航至对应站点。

![Chrome中由由Browser Process的UI Thread判断输入是URL还是搜索查询](https://upload-images.jianshu.io/upload_images/20154859-20a2dba615b4cff8.png?imageMogr2/auto-orient/strip%7CimageView2/2/w/1240)

**2.检查是否注册过Service Worker：**
Browser Process的UI Thread将URL发送给Browser Process的Network Thread，同时查找可用进程或启动新的渲染器进程。Browser Process的Network Thread会判断该域是否注册了Service Worker，如果注册过Service Worker，则通知Renderer Process的Service Worker Thread执行注册的Service Worker代码。此时还没有Memory Cache（Renderer Process的Blink Thread会存有一份Memory Cache，它有自己缓存策略，我们无法直接操作它），之后的请求会先尝试从Memory Cache中获取，然后尝试从Disk Cache中获取，最终才真正发起网络请求。

**3.进行DNS解析：**
![Chrome中由Browser Process的UI Thread通知Network Thread调用系统的DNS解析器进行解析](https://upload-images.jianshu.io/upload_images/20154859-e57c37cac1443f3a.png?imageMogr2/auto-orient/strip%7CimageView2/2/w/1240)
通常我们会在地址栏中输入域名而不是IP，当用户输入的是域名时，则需要进行DNS解析来获取IP。此时浏览器自身不会进行DNS解析，而是由Browser Process的UI Thread通知其Network Thread调用操作系统的DNS解析器进行解析，DNS解析的具体流程如下：

**I.读取浏览器的DNS缓存**：为了减小DNS解析带来的延迟，浏览器自身会缓存DNS解析结果，有效期通常为1分钟，缓存未命中则进入下一步；
**II.读取操作系统的/etc/hosts文件**：用户可以为操作系统配置指定的DNS解析规则，当hosts文件不存在当前域名的映射时，进入下一步；
**III.操作系统的DNS解析器发起DNS解析**：当以上步骤都没能成功完成DNS解析时，才会真正开始调用操作系统的DNS解析器进行解析，首先操作系统的DNS解析器会缓存一定数量的DNS解析结果，缓存未命中则进入下一步；然后操作系统的DNS解析器会读取路由器的DNS缓存，缓存未命中则向本地DNS服务器（可以通过操作系统设置）发起查询，本地DNS服务器通常是ISP（互联网服务提供商，如电信、移动等）的DNS缓存服务器，本地DNS服务器缓存中没有则向根域名服务器（负责管理其它顶级域名服务器）发起查询，根域名服务器根据会返回对应的顶级域名服务器（如.com）的IP，由本地DNS服务器再向顶级域名服务器发起查询，未查询到则返回对应的主域名（如example.com）服务器的IP，由本地服务器向主域名服务器发起查询，如此循环直到解析成功。

**学以致用**：
DNS解析带来的延迟可能会在1ms（本地缓存）到几秒之间，可能会使用户感到较大的延迟，对此浏览器与操作系统的DNS解析器帮助我们做了缓存，除此之外，我们还可以通过DNS预取来优化这个环节，目前大部分浏览器都支持手动DNS预取（自动DNS预取：Chrome还会自动存储浏览器最后浏览的10个域名，当下次启动时，预先解析这些域名），它可以帮助我们对指定域名进行预先解析，从而加快DNS解析速度，详情参阅[这里](https://www.chromium.org/developers/design-documents/dns-prefetching)，它适用于包含较多外链的页面，比如搜索结果页。我们可以通过添加`<meta http-equiv="x-dns-prefetch-control" content="on/off">`来告知浏览器是否启用DNS预取，通过添加`<link rel="dns-prefetch" href="http://example-domain.com/">`来手动进行DNS预取，结合`<link rel="preconnect" href="https://fonts.googleapis.com/" crossorigin>`还可以使浏览器预先与服务器建立连接，如果站点是通过HTTPS服务的，还可以预先执行TLS握手。

**4.与服务器建立连接**：
通过上一步拿到的IP地址和端口号（如果未指定端口号，根据协议的不同，则使用不同的默认端口号，HTTP协议为80端口，HTTPS协议为443端口），浏览器将与服务器建立TCP连接，了解连接过程首先需要理解以下概念：

- TCP简介：TCP属于TCP/IP协议模型中的传输层，它的数据是通过名为IP分组的小数据块传输的。HTTP要发送一条报文时，会以数据流（数据流指的是只能以事先规定好的顺序被读取一次的数据的一个序列）的形式将报文数据的内容发送给TCP，TCP收到数据流后，会将这些数据分为多个TCP段，每个TCP段都会由一个IP分组承载，然后通过网络进行传输。
- **套接字：在操作系统中，通常会为应用程序提供应用程序接口（API），其中就包含套接字接口（socket API）。应用程序可以通过套接字接口，来使用网络套接字，以进行数据交换。在套接字接口中，以IP地址及端口组成套接字地址（socket address）。远程的套接字地址，以及本地的套接字地址完成连线后，再加上使用的协议（protocol），这个五元组（five-element tuple），作为套接字对（socket pairs），之后就可以彼此交换数据。套接字接口会提供`socket()`（创建一个新的套接字）、`bind()`（绑定到本地主机的指定端口）、`listen()`（允许套接字进行连接）、`accept()`（等待连接）、`connect()`（创建一条与其它套接字的连接）等函数，浏览器便是通过操作系统调用操作系统的套接字接口来建立TCP连接的。**

TCP连接从建立到断开的过程大致如下：

- 服务器端：首先服务器的应用程序启动时（通常是Nginx/Apache httpd）会创建一个新的socket（套接字），将其绑定（bind）到指定端口上（如80），然后允许其进行连接（listen），最后等待连接（accept）；
- 客户端：TCP连接是由客户端发起的，客户端（浏览器为其中一种）会创建一个新的socket，将其绑定（bind）到一个随机端口上，然后与服务器的socket进行连接（connect）；
![TCP的三次握手与四次挥手](https://upload-images.jianshu.io/upload_images/20154859-3bb8814c1809785f.png?imageMogr2/auto-orient/strip%7CimageView2/2/w/1240)

- 三次握手：当客户端的socket调用connect()函数时，将会触发三次握手，大致流程如下：
  1.第一次握手(SYN=1, seq=x)：客户端发送一个SYN标志位置1、seq=x（随机数）的TCP段，发送完毕后客户端进入 `SYN_SENT` 状态。
  2. 第二次握手(SYN=1, ACK=1, seq=y, ack=x+1)：服务器返回一个 SYN 标志位和 ACK 标志位均置1，seq=y（随机数），ack=x+1的TCP段， 发送完毕后服务器端进入 `SYN_RCVD` 状态。
  3.第三次握手(ACK=1，seq=x+1，ack=y+1)：客户端再次发送一个SYN 标志位置0，ACK 标志位置1，seq=x+1，ack=y+1的TCP段，发送完毕后客户端进入 `ESTABLISHED` 状态，当服务器端接收到这个包时，也进入 `ESTABLISHED` 状态，TCP 三次握手结束。

  - SYN：同步标志位，表示请求建立连接
  - seq: 序列号，用来保证数据的有序性和不丢失
  - ACK: 确认标志位，表示同意建立连接
  - ack: 确认号，用来告诉对方我期望收到的下一个序列号是多少
  - 为什么不能是两次握手?: 我们无法保证请求链路的稳定性，客户端没收到服务端的返回，可能会重发建立连接的请求，如果服务端重复收到请求，就会浪费资源等待回复
  - 为什么不能是四次及以上握手？：第二次握手时，服务端把确认请求和发起请求合并了，提高效率

- 四次挥手：当客户端或服务端的socket调用connect()函数时，将会触发四次挥手，以客户端发起断开连接为例，大致流程如下：
  1.第一次挥手(FIN=1，seq=x)：客户端会发送一个 FIN=1，seq=x的TCP段，发送完毕后客户端进入 `FIN_WAIT_1` 状态。
  2.第二次挥手(ACK=1，ack=x+1)：服务端收到客户端的 FIN 包后，会发送一个ACK=1，ack=x+1的TCP段，发送完毕后服务器端进入 `CLOSE_WAIT` 状态，客户端接收到服务端的 ACK 包后，进入 `FIN_WAIT_2` 状态，等待服务器端的FIN包。
  3.第三次挥手(FIN=1，seq=y)：服务器端向客户端发送一个FIN=1，seq=y的TCP段，发送完毕后服务器端进入 `LAST_ACK` 状态，等待来自客户端的最后一个TCP段。
  4.第四次挥手(ACK=1，ack=y+1)：客户端接收到来自服务器端的FIN包后，会发送一个ACK=1，ack=y+1的TCP段，并进入 `TIME_WAIT`状态。服务器端接收到这个TCP段之后，进入 `CLOSED` 状态。客户端等待了2MSL之后，没有收到服务器端的TCP段 ，认为服务器端已经正常关闭连接，于是自己也关闭连接，进入 `CLOSED` 状态。
- 为什么需要三次握手和四次挥手？：TCP是可靠性连接，但是IP分组并不能保证不丢失以及按序到达服务端，因此需要考虑包丢失或者延迟到达的可能性：
  - 第一次握手的意义：客户端向服务端请求建立连接，当这个IP分组丢失时，客户端会定时重发直到收到服务端返回的确认包；
  - 第二次握手的意义：服务端确认收到客户端的建立连接请求，并同步TCP段序号，当这个IP分组丢失时，服务端会定时重发直到收到客户端返回的确认包；
  - 第三次握手的意义：很显然第一次与第二次握手是必要的，有疑惑的在于为什么服务端还需要进行一次确认，这是因为服务端必须确认客户端收到了自己的seq，假如服务端返回的确认包（即第二次握手）丢失了，会导致服务端的seq在双方无法达成一致，从而出错，所以必须确认客户端成功收到了这个确认包；
  - 第一次挥手的意义：客户端向服务端请求断开连接；
  - 第二次挥手的意义：服务端接收到客户端的断开连接请求，但是这时候可能存在还没发送出去的TCP段，所以服务端只是进入等待关闭状态，并发送ACK包给客户端，此时客户端进入等待结束状态，等待服务端的FIN包。
  - 第三次挥手的意义：当服务端确认可以断开连接后，会发送一个FIN包给客户端，此时客户端会发送一个ACK包给服务端，但不会立即进入关闭状态，而是会等待2MSL（通常为两分钟），避免短时间内重新建立相同IP及端口的连接。
  - 第四次挥手的意义：由于IP分组可能会丢失，所以服务端必须在收到最后一个ACK包后确认客户端收到了FIN包后才能进入关闭状态，否则客户端未收到FIN包将会一直等待，而此时服务端已关闭，不会重发FIN包。
- **主要延迟：
  1.握手延迟：小的HTTP事务可能会在TCP建立的三次握手上花费50%甚至以上的时间，所以需要复用现有连接来减小请求延迟；
  2.TCP慢启动：TCP连接具有自我调谐机制，起初会限制连接的最大传输速度，避免网络的突然过载和拥塞，然后每次成功接收一个分组，发送端的最大传输速度限制就会提高，所以复用旧连接可以减小TCP慢启动带来的延迟；**

**学以致用**：TCP属于TCP/IP模型的传输层，前端在传输层并不能做什么，通常浏览器会默认启用```keep-alive```或HTTP/2，来尽可能的减少TCP连接的数量，我们能做的就是“域名收敛”，尽量将静态资源放在同一个域名下。

**5.发起HTTP请求获取响应并处理请求响应**：
在上一步建立好连接后，浏览器将发送HTTP请求获取响应，响应头部中的Content-Type标头会标识数据的[MIME Type](https://developer.mozilla.org/en-US/docs/Web/HTTP/Basics_of_HTTP/MIME_types)，但是由于可能会丢失或错误，所以此时会进行MIME Type嗅探，详情参阅[这里](https://cs.chromium.org/chromium/src/net/base/mime_sniffer.cc?sq=package:chromium&dr=CS&l=5)。
如果响应是HTML文件，则下一步是将数据传递到渲染器进程，但是如果它是zip文件或其他文件，则意味着这是一个下载请求，因此他们需要将数据传递到下载管理器。

**学以致用**：针对网络请求的优化是前端性能优化的主要方向之一，包括使用CDN、缓存等，其主要目的也是为了减小网络开销带来的延迟，而HTTP是Web应用的主要通信方式，所以在这步我们可以做的事情有很多，大致如下：

- 使用CDN：[CDN](https://zh.wikipedia.org/wiki/%E5%85%A7%E5%AE%B9%E5%82%B3%E9%81%9E%E7%B6%B2%E8%B7%AF)可以帮助我们减小客户端建立TCP连接的时间及加快客户端TCP传输的速度，它的加速原理简单来说就是为用户提供距离较近、较为顺畅的网络节点的缓存，它适用于用户较多、不集中于某区域，且不敏感的数据。

  - 减少HTTP请求个数：
    - 使用持久连接：HTTP/1.0+中需要使用Connection: Keep-Alive请求头声明使用持久连接，但从HTTP/1.1开始持久连接成为了默认行为，它可以在短时间内复用TCP连接，从而减小上一步中提到的两个主要TCP延迟。
    - 使用雪碧图：合并图片然后通过CSS样式显示图片的一部分，这种方法可以减小请求图片的请求个数。

  - 减小HTTP请求体积：
    - 开启GZIP压缩
  - 增加并发连接数：浏览器对单个域名通常限制2~8个并发的TCP连接，为了突破这个限制，可以使用域名分片，即使用多个域名映射同个服务，值得注意的是，这仅在HTTP/1.1中适用，在 HTTP/2/3 中本就有多路复用，所以这个方法会变成反向优化。
  - 客户端缓存数据：
    - Memory Cache：Blink Thread会在内存中保留一份缓存，可以通过添加`<link rel="preload" href="http://example-domain.com/example.png">`或者`<link rel="prfetch" href="http://example-domain.com/example.png">`来预加载一些静态资源，通过`<link rel="prerender" href="http://example-domain.com/example.html">`来预渲染一些页面，它们会先保存在Memory Cache中，使用时再去读取，但是都要保证这些资源都将被使用到，页面都将被导航到。
    - Service Worker：通过注册Service Worker，可以自定义控制缓存，仅适合Disk Cache无法满足需求时使用；
    - Disk Cache：通过设置响应头部，可以让客户端缓存指定文件于磁盘中。
  - 使用HTTP2/3：使用HTTP2就可以直接实现上面所述的减少HTTP请求个数和增加并发连接数，并且它是二进制协议并且使用字典映射压缩了请求头，也减小了传输的体积，此外还有其它很多优化，它最大的问题在于兼容性。

**6.查找或启动Renderer Process**：
由于网络请求可能需要几百毫秒才能获得响应，因此当UI Thread在向Network Thread发送URL请求时，它就同时开始查找或启动Renderer Process。如果一切按预期进行，则当Network Thread接收到数据时，Renderer Process已经处于备用位置。如果导航重定向到其它站点，则可能不会使用此备用过程，而是另起一个Renderer Process。

**7.渲染页面**：
现在已经准备好数据和Renderer Process，Renderer Proces开始渲染页面。我们的大部分代码都将在这一步被渲染引擎解析并最终显示在屏幕上，它的主要流程如下：
![Blink渲染流程](https://upload-images.jianshu.io/upload_images/20154859-730c781561eacd8c.png?imageMogr2/auto-orient/strip%7CimageView2/2/w/1240)

- 构建DOM树：
![构建DOM树](https://upload-images.jianshu.io/upload_images/20154859-bc165f0954307f81.png?imageMogr2/auto-orient/strip%7CimageView2/2/w/1240)

1. **转换：** 浏览器从磁盘或网络读取 HTML 的原始字节，并根据文件的指定编码（例如 UTF-8）将它们转换成各个字符。
2. **标记化：** 浏览器将字符串转换成 [W3C HTML5 标准](http://www.w3.org/TR/html5/)规定的各种标记，例如，“`<html>`”、“`<body>`”，以及其他尖括号内的字符串。每个标记都具有特殊含义和一组规则。
3. **词法分析：** 发出的标记转换成定义其属性和规则的“对象”。
4. **DOM 构建：** 最后，由于 HTML 标记定义不同标记之间的关系（一些标记包含在其他标记内），创建的对象链接在一个树数据结构内，此结构也会捕获原始标记中定义的父项-子项关系：*HTML* 对象是 *body* 对象的父项，*body* 是 *paragraph* 对象的父项，依此类推。

- 构建CSS树：
![构建CSS树](https://upload-images.jianshu.io/upload_images/20154859-443a00d0a1067df6.png?imageMogr2/auto-orient/strip%7CimageView2/2/w/1240)

- 构建渲染树（布局树）：
在现代浏览器中，构建 DOM 树和构建 CSSOM（CSS 对象模型）树是同时进行的，当 DOM 树和 CSSOM 树都构建完成后，浏览器就会将它们合并，开始构建渲染树，这个过程通常被称为 Style Recalculation（样式计算） 阶段， CSS 设置了 ```display: none``` 的元素及其子元素，会被完全排除在渲染树之外，设置为 ```visibility: hidden``` 或 ```opacity: 0``` 的元素会保留在渲染树中，因为它们虽然看不见，但仍然在页面中占据空间。
![构建渲染树](https://upload-images.jianshu.io/upload_images/20154859-562a82d895993eb3.png?imageMogr2/auto-orient/strip%7CimageView2/2/w/1240)

- 布局：浏览器遍历渲染树，计算每个节点在屏幕上的确切大小、几何位置和坐标。
- 分层：把页面拆分成多个独立的合成层（Compositing Layers）。
- 切分图块：合成层可能非常大（比如一个几千像素高的可滚动网页），但用户的屏幕（视口）只有那么大。主线程会将图层信息交给合成线程（Compositor Thread）。合成线程会把每个图层切成一个个小的图块（Tiles））。
- 光栅化：把图块（矢量图形、文字指令）转换成位图（Pixels，像素点阵）的过程。
- 合成与绘制：将这些已经单独绘制好的图层，按照正确的层级顺序（z-index）叠加在一起，当视口内所有必要的图块都被栅格化为位图后，合成线程会收集这些图块在屏幕上的位置信息，生成一系列的绘制指令（Draw Quads）。
- 显示：显卡（GPU）将这些图层合并，最终把像素点绘制到你的屏幕上。

**学以致用**：

1. 如何写出丝滑的动画与交互：在做大屏可视化、H5 翻页、轮播图或复杂动效时，放弃使用 left/top/margin，而是转用 transform (translate/scale) 和 opacity，因为left会触发整条流水线的回流（Reflow），让主线程卡顿，而 transform 能直接走合成更新阶段（Composite），由合成线程在 GPU 里完成，不占主线程，能稳稳跑到 60fps 甚至 120fps；
2. 精准驾驭“硬件加速”而不崩坏内存：在长列表滚动、3D动效卡顿时去使用 will-change: transform 提前触发独立分层。但不能滥用它（比如给页面上几百个元素都加 will-change），因为“合成阶段”需要将图层栅格化（Rasterization）为位图。每一个合成层都会白白占用大量的 GPU 显存，滥用会导致移动端（尤其是低端安卓机）闪退、白屏或手机发烫；
3. 解决 JavaScript 导致的页面卡死与掉帧：当用户反馈“点击按钮页面卡住”或“滚动很卡”时，打开 Chrome DevTools 的 Performance 面板，去看是不是 Main Thread（主线程） 出现了长任务（Long Task），或者是不是频繁触发了 Layout（布局），在循环里读取了 element.offsetHeight 并立刻修改 element.style.width。这是强制同步布局（Forced Synchronous Layout），也就是在主线程里频繁触发了回流，应该通过将读取操作移出循环，或者使用 requestAnimationFrame 来完美解决；
4. 诊断“隐式合成”导致的层级混乱（z-index 失效）：有时候明明给 A 元素设置了 z-index: 9999，但它依然被 B 元素盖住了，或者页面某些元素滚动时突然消失，因为合成阶段的 Layer 机制。如果 B 元素因为某种原因（如使用了 transform）升为了“独立合成层”，哪怕它的 z-index 比 A 低，它也可能在 GPU 渲染时跑到 A 的前面（即隐式合成造成的层叠上下文错乱）。你会通过 DevTools 的 Layers 面板 抓出这个“叛逆”的图层；
5. 看框架：理解 React 18 要搞 Fiber 和并发模式（就是为了不让 JS 长期霸占主线程，给浏览器留出时间做布局和绘制）；
6. 看跨端：当你接触 Electron、React Native、Flutter 或者小程序的双线程模型时，你会发现它们的底层架构（如小程序把 JS 逻辑层和 UI 渲染层分开）都是为了解决浏览器主线程容易被 JS 卡死这一原生痛点。

**8.离开页面**：

- 从Renderer Process启动的（例如用户单击链接或运行window.location = "<https://newsite.com"）：选项卡内部的所有内容（包括JavaScript代码）都由Renderer> Process处理，因此，当有新的导航请求出现时，Browser Process必须与当前Renderer Process进行核对，Renderer Process需要检查当前站点是否注册了 [`beforeunload`](https://developer.mozilla.org/en-US/docs/Web/Events/beforeunload)事件，然后已相同的步骤处理新的导航。
- 在地址栏中输入一个新的URL：当将新导航导航到与当前渲染站点不同的站点时，将调用一个单独的Renderer Process来处理新导航，同时保留当前Renderer Process来处理诸如unload的事件。

## 浏览器的存储

- Manifest (应用缓存/AppCache)：
  技术本质：早期 HTML5 引入的一种离线存储机制，通过一个 .manifest 文本文件声明哪些资源需要被浏览器强缓存。由于其设计存在严重的“全盘皆活或全盘皆死”、无法局部更新、路由无法定制等架构缺陷，在现代浏览器标准中已被完全废弃（Deprecated）。
  **学以致用**：不要在任何新项目中使用它。如果遇到维护十几年前的老旧系统（如老旧的离线 iPad 展厅应用），需注意其更新必须修改 manifest 文件本身的 MD5。现代项目中，应全面拥抱 Service Workers 作为其替代方案。
- Service Workers (Cache Storage)：
  技术本质：作为浏览器架构中的一个独立工作线程（Worker Thread），它可以拦截运行域下的所有网络请求，并配合 Cache Storage 接口实现极其高阶、灵活的资源级缓存管理。它独立于主线程，不会阻塞 DOM 渲染，支持完全自定义的缓存策略（如网络优先、缓存优先、Stale-While-Revalidate）。
  **学以致用**：用于构建 PWA（渐进式 Web 应用）、实现真正的离线可用（Offline First）、大文件分片秒传的断点续传缓存，以及离线消息推送。在日常 H5 性能优化中，可通过它缓存长期不动的底层依赖库（如打包后的 vendor.js），彻底跳过网络层，实现首屏毫秒级冷启动。
- Local Storage：
  技术本质：基于键值对（Key-Value）的同步（Synchronous）字符串存储机制。每个域名通常有 5MB 左右的容量限制。其底层直接操作磁盘 I/O 且运行在主线程上，这意味着高频或大数据的读写会直接阻塞主线程的 JavaScript 执行，进而导致页面卡顿、掉帧。
  **学以致用**：仅用于存储轻量、高频、跨会话的非敏感配置数据，如用户的持久化皮肤主题（暗黑模式）、用户的个人基础设置（语言偏好）、本地化埋点日志的临时暂存等。切忌将大型 JSON 对象、Base64 图片或频繁变动的数据塞入其中，且读取时建议做好 try-catch 以防容量超限（QuotaExceededError）。
- Session Storage：
  技术本质：其底层存储原理、同步阻塞特性以及容量限制与 Local Storage 完全一致，但在生命周期架构上具有严格的“标签页（Tab）作用域”。它不仅在浏览器关闭时被清空，哪怕是在同一个浏览器中打开两个相同 URL 的标签页，它们的 Session Storage 也是完全隔离的（通过 window.open 派生的同源标签页在初始化时会复制一份，但随后独立）。
  **学以致用**：非常适合用来存储单次会话（Tab内）的状态控制管理。例如：多步骤表单填写的中间状态（防止用户误刷新页面后数据丢失）、单页应用（SPA）中的页面滚动位置（Scroll Position）恢复、或者单次登录期间的临时活动状态标记。
- IndexedDB：
  技术本质：浏览器原生的异步（Asynchronous）对象数据库。它支持事务（Transactions）、索引查询、甚至可以存储二进制数据（Blob/ArrayBuffer）。它的存储空间极大（通常可达用户硬盘剩余空间的 20% 以上，支持数百MB甚至GB级别），且由于所有操作都是异步的，绝对不会阻塞主线程。
  **学以致用**：适用于数据密集型、需要离线复杂计算的前端应用。例如：Web 端富文本/Markdown 编辑器的本地草稿箱自动保存、低代码搭建平台的离线资产库、离线地图应用的数据瓦片缓存、前端轻量级日志分析系统，或者需要在前端缓存大量用户历史结构化数据的 CRM 系统。在实际开发中，建议配合 localForage 或 idb 库来简化其繁琐的原生 DOMString 异步回调 API。
- Web SQL：
  技术本质：早期浏览器为了在前端引入 SQL 关系型数据库而做出的尝试（底层基于 SQLite）。但由于该标准本质上被单家数据库引擎（SQLite）所垄断，不符合 W3C 开放标准的多元化原则，目前已被 W3C 标准正式废弃，且在 Chrome 等主流浏览器中已被完全移除。
  **学以致用**：在任何现代前端技术选型中直接排除。如果应用确实需要高强度的关系型数据库功能（如在前端运行复杂的 SQL 联表查询），现代的架构解决方案是使用 WebAssembly（WASM）技术将 SQLite 编译并运行在浏览器中（如 @sqlite.org/sqlite-wasm 或 sql.js），并以 Origin Private File System (OPFS) 或 IndexedDB 作为其底层的物理存储介质。
- Cookies：
  技术本质：浏览器中最古老、最具有“网络属性”的存储机制。它的容量极小（通常每个域名不能超过 4KB，数量限制在 20~50 个）。它的核心特性是会自动附带在每一次同源的 HTTP 请求头中（Cookie Header）发往服务端，这意味着它会直接占用极其宝贵的网络带宽。
  **学以致用**：只用来做身份认证与安全鉴权（如 Session ID、Token），绝不用作普通的数据存储。在实践中必须严格配置安全属性：开启 HttpOnly 防止 XSS 攻击盗取 Cookie；开启 Secure 确保只在 HTTPS 下传输；合理配置 SameSite=Lax/Strict 来有效防御 CSRF 跨站请求伪造攻击。

## 浏览器的安全策略

- 同源策略 (Same-Origin Policy / SOP)：
  技术本质：浏览器最核心、最基本的基石级安全模型。它规定：如果两个 URL 的协议（Protocol）、域名（Domain）和端口（Port）有任何一个不同，它们就属于“不同源”。浏览器在底层会对跨源操作进行严格限制，主要隔离了三个层面：DOM 访问（无法操作跨域页面的 DOM）、Cookie/LocalStorage 等存储访问、以及网络请求（默认阻止跨域读取 XHR/Fetch 的响应结果）。
  **学以致用**：理解 SOP 是所有 Web 开发的基础。前端需要明白，SOP 并不是阻止跨域请求的发送，而是阻止了浏览器去读取跨域返回的响应数据。当你在开发中遇到跨域报错时，不要试图在前端通过修改 document.domain（该特性由于安全隐患在现代浏览器中已被废弃）来绕过，而应通过合规的“跨域解法”（如配置反向代理或下述的 CORS）来解决。
- CORS (跨源资源共享 / Cross-Origin Resource Sharing)：
  技术本质：为了打破同源策略的死板限制，W3C 引入的一种基于 HTTP 响应头部的协商放行机制。它允许服务端通过声明特定的响应头，主动告诉浏览器：“我信任这个外源，允许它读取我的数据”。为了安全，对于一些可能会对服务器数据造成副作用的请求（如 PUT/DELETE，或自定义了请求头的 POST），浏览器在底层会先发送一个 OPTIONS 预检请求（Preflight Request），只有当预检通过后，才会发送真正的业务请求。
  **学以致用**：在前后端分离的架构中，必须精确配置生产环境的 CORS 头。严禁在生产环境配置 Access-Control-Allow-Origin: * 且同时设置 Access-Control-Allow-Credentials: true（浏览器底层其实直接禁止了这种危险组合），这会导致用户凭证（Cookie）暴露。正确的做法是，在后端动态校验请求的 Origin，如果是可信域名，再动态写入该 Origin。同时，合理设置 Access-Control-Max-Age（预检请求缓存时间），避免每个业务请求前都多发一次 OPTIONS，降低线上网络开销。
- CSP (内容安全策略 / Content Security Policy)：
  技术本质：浏览器为了彻底防御恶意脚本注入而引入的一道坚固的动态防护网。它通过 HTTP 响应头 Content-Security-Policy 或 `<meta>` 标签，显式地告诉浏览器：“当前页面只能加载和执行哪些来源的 JS/CSS/图片，只能向哪些域名发起连接”。一旦浏览器发现页面上有不符合 CSP 白名单的资源（例如攻击者注入的恶意内联 `<script>`），就会拒绝执行并直接报错。
  **学以致用**：CSP 是防御 XSS 攻击的终极底牌。在实际项目中，应在网关层（如 Nginx）统一配置严格的 CSP 策略。推荐的最佳实践是禁用内联脚本（禁止 unsafe-inline），所有 JS 必须通过外部文件加载，或者为合法的内联脚本配置 nonce（随机哈希安全令牌）。同时，可以开启 report-uri 或 report-to 指令，当线上发生任何违反 CSP 策略的脚本企图执行时，浏览器会自动异步向你的监控后台发送报警日志，实现线上安全态势感知。
- CSRF (跨站请求伪造 / Cross-Site Request Forgery)：
  技术本质：攻击者利用了浏览器“在发送同源/跨端 HTTP 请求时会自动携带对应域名 Cookie”的这一底层自动化机制。受害者在 A 网站登录并保留了 Cookie，随后不小心访问了恶意网站 B，网站 B 伪造了一个向 A 网站转账的请求。由于浏览器的自动携带特性，A 网站的服务器会误以为这是受害者本人的合法操作，从而导致越权风险。
  **学以致用**：现代前端防范 CSRF 主要有两大杀招。第一，全面拥抱 Cookie 的 SameSite 属性：现代浏览器默认将未设置 SameSite 的 Cookie 视为 SameSite=Lax，这意味着第三方网站跨站发起 POST 请求时默认不会携带该 Cookie，直接废了 CSRF 的武功。第二，使用双标票机制（CSRF Token）：由于 CSRF 只能“伪造自动携带”，但由于同源策略限制，攻击者无法读取 A 网站的 DOM。因此，前端在发起非 GET 请求时，在请求头或请求体中手动附带一个从页面渲染时拿到的随机 Token，后端进行比对校验。
- XSS (跨站脚本攻击 / Cross-Site Scripting)：
  技术本质：网络安全领域的“万恶之首”，其本质是代码注入。由于前端未对用户输入或恶意数据进行严格过滤和转义，导致攻击者的恶意 JS 代码被混入到 HTML 文档中。浏览器无法分辨这段代码是原本业务的一部分还是攻击者注入的，于是在主线程上欢快地执行了它，从而导致攻击者可以任意窃取页面的 LocalStorage、Cookie（若未设 HttpOnly）或者伪造用户操作。
  **学以致用**：防范 XSS 贯穿前端整个研发周期。首先，坚决不要盲目使用 innerHTML 或 Vue 的 v-html / React 的 dangerouslySetInnerHTML，如果必须渲染富文本，必须先使用 DOMPurify 等库进行严格的消毒（Sanitize）过滤。其次，任何需要动态展示的用户输入数据，在输出到 HTML 页面、属性、或者 JS 变量中时，必须进行对应的 HTML/JS 实体转义。最后，对敏感 Cookie（如登录态 Token）必须强制开启 HttpOnly，确保即使用户页面被攻破，攻击者也绝对无法通过 document.cookie 偷走最关键的凭证。
- CORB (跨源读取阻止 / Cross-Origin Read Blocking)：
  技术本质：这是现代浏览器（特别是 Chromium 架构）为了应对 Spectre、Meltdown 等 CPU 幽灵/熔断漏洞引发的侧信道攻击而引入的底层硬件级防御机制。当页面通过 `<img src="...">` 或 `<script src="...">` 等合法跨域标签尝试加载跨域资源时，如果后端返回的数据类型是敏感的 HTML、JSON 或 XML（且带有 X-Content-Type-Options: nosniff），CORB 机制会在数据到达渲染进程之前拦截它，将数据躯体（Body）替换为空，防止恶意的渲染进程通过内存缓存分析手段窃取这些敏感数据。
  **学以致用**：理解 CORB 可以帮你避开很多现代浏览器的“诡异 Bug”。如果你在前端使用 `<img>` 标签去加载一个后端的 API 接口（该接口其实返回的是 JSON 格式的错误信息或用户数据），在控制台你可能会看到一条 CORB 拦截的警告，且图片加载失败。作为前端，当需要加载跨域的静态资源（如图片、视频、字体）时，必须确保后端的 Content-Type 响应头与实际的资源格式绝对匹配（如图片必须是 image/png），并且规范化前后端的数据接口设计，不要混用媒体标签和数据接口。
