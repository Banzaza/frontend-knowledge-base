# HTML

## doctype(文档类型) 的作用是什么？

告诉浏览器使用哪种规范来解析页面，它会决定浏览器的渲染模式，标识文档所使用的规范版本。

## 浏览器标准模式 (standards mode) 、几乎标准模式（almost standards mode）和怪异模式 (quirks mode) 之间的区别是什么？

1. 盒模型（Box Model）的解析差异
    - 怪异模式：采用早期的 IE 盒模型（Border-box）。如果你设置 width: 100px; padding: 10px; border: 5px solid;，整个元素的实际总宽度就是 100px，内容区域会被压缩。
    - 标准模式与几乎标准模式：采用 W3C 标准盒模型（Content-box）。同样的设置，元素的实际总宽度会变成 100 + 20 + 10 = 130px。

2. 几乎标准模式的由来：图片白边问题（Images inside Table Cells）
几乎标准模式与标准模式在 99% 的规则上完全相同，它存在的唯一原因是为了解决一个历史布局痛点：
    - 在标准模式下，图片（`<img>`）作为行内元素，默认会按照字体的基线（Baseline）对齐。这会导致图片下方留出一段为了容纳英文字母尾巴（如 g、j、p、y）的“空隙”，如果图片放在表格单元格（`<td>`）中，会导致单元格底部出现莫名其妙的白边。
    - 许多老网站在过渡到标准模式时，这种白边破坏了原有的切图拼接布局。于是浏览器引入了几乎标准模式：它遵循所有的现代标准，唯独在处理单元格内的图片时，去掉底部的基线空隙，让图片完美贴合单元格边缘。

3. 其它怪异模式的“迷惑行为”
在怪异模式下，浏览器还会激活许多非标准的旧特性：
    - margin: 0 auto 失效：在怪异模式下，无法通过该属性让块级元素在父元素中水平居中，必须在父元素上设置 text-align: center。
    - 百分比高度失效：如果父元素没有明确设置固定高度（height），子元素设置 height: 100% 将直接失效。
    - 字体大小不继承：表格（`<table>`）内部的文本不会继承父元素的字体大小，必须单独为表格写样式。

## 如果网页内容需要支持多语言，你会怎么做？

1. 技术栈与框架选型
    - Vue 生态：使用 vue-i18n
    - React 生态：使用 react-i18next 或 FormatJS (react-intl)
    - 原生 / 轻量项目：使用 i18next

    语言包管理, 将所有的文案从代码中解耦，提取为独立、结构化的 JSON 文件（按模块拆分，便于翻译团队维护）
2. 核心技术痛点的处理
    多语言绝对不只是“直译文字”，必须处理以下复杂场景：
    - 复数问题 (Pluralization)：英文有单复数（1 item vs 2 items），阿拉伯语有 6 种复数形式。必须利用 i18n 库自带的复数判定机制。
    - 动态插值与格式化：
    - 日期/时间：使用原生 Intl.DateTimeFormat，不同国家习惯不同（如 2026/11/04 vs 04/11/2026）。
    - 货币/数字：使用 Intl.NumberFormat 处理千分位和货币符号（如 ￥1,000.00 vs $1,000.00）。
3. URL 路由设计与 SEO 优化（至关重要）
    为了让搜索引擎（如 Google）能够正确抓取不同语言版本的页面，必须在 URL 中体现语言，并做好元数据配置。
    - 子目录形式（最常用，推荐）：://example.com、://example.com。
    - 子域名形式：://example.com、://example.com。

    标签与头信息配置

    - HTML lang 属性：动态修改 `<html>` 标签的 lang 属性（如 `<html lang="en">`），这不仅利于 SEO，也能帮助屏幕阅读器（无障碍）正确发音。
    - hreflang 标签：在 `<head>` 中配置，告诉搜索引擎各语言版本之间的对应关系，避免被判定为重复内容

4. 语言的检测与路由重定向策略
    当用户首次访问网站时，系统应如何决定展示哪种语言？
    1. 第一优先级：URL 路径。如果用户直接访问 ://example.com，无条件展示英文。
    2. 第二优先级：持久化存储。检查用户之前是否手动切过语言（读取 localStorage 或 Cookie）。
    3. 第三优先级：浏览器默认语言。读取请求头 Accept-Language 或前端 navigator.language。如果支持该语言，则自动重定向到对应的语言路由（如 /zh/）；如果不支持，则降级到系统默认语言（通常是英文 /en/）。
5. CSS 布局与体验适配（避免排版灾难）
    - 不同语言的文本长度和阅读习惯差异巨大，CSS 必须具备“弹性”：
    - 拒绝固定宽度：德语、俄语的单词极长，中文只需几个字。给按钮、导航栏设置固定宽度会导致严重的文字溢出。应使用 min-width、flexbox 或 grid 布局。
    - 文字折行处理：对长单词语种使用 word-break: break-word; 或 hyphens: auto;（自动加连字符）。
    - 使用 CSS 逻辑属性：用 margin-inline-start 代替 margin-left，以自动适配从右往左读的语种（RTL，如阿拉伯语、希伯来语）。当 html[dir="rtl"] 被激活时，整个页面布局会自动镜像反转。
6. 性能优化：按需加载（Lazy Loading）
    不要把所有语种的 JSON 语言包一次性打包到代码里！如果网站有 20 种语言，一次性加载会导致首屏体积爆炸，应该利用 Webpack / Vite 的动态导入（Dynamic Import），当且仅当用户切换或命中某种语言时，才通过网络异步加载对应的语言包。

## 在设计和开发多语言网站时，有哪些问题你必须要考虑？

1. 架构与工程层面的问题

    多语言资源包的加载性能：
    - 问题：如果把所有语种的文案全部打包进一个 JS 文件，随着语种和业务增加，首屏文件体积会爆炸。
    - 应对：必须设计异步按需加载（Lazy Loading）。只有在用户切换到对应语种时，才去服务器请求该语种的 JSON 配置文件。
    硬编码（Hardcoding）的清理机制：
    - 问题：开发人员很容易顺手在组件里写死中文（如 `<span>提交</span>`），漏掉国际化键值。
    - 应对：引入 Linter 工具（如 eslint-plugin-vue-i18n 或 eslint-plugin-react-i18n），在代码提交或构建时强制检测未提取的硬编码文本。
    第三方服务与依赖的国际化：
    - 问题：你使用了第三方的日期组件、地图、验证码（如 Google reCAPTCHA）或图表，它们的提示文字如何跟随网站语言一起切换？
    - 应对：在初始化这些第三方 SDK 时，必须动态传入当前系统的语言变量（如 lang=en）。

2. 界面布局与 CSS 的“灾难预案”

    不同语言的物理长度和阅读习惯差异巨大，UI 绝对不能做“一鼓作气”的死板设计。
    UI 空间的“伸缩性”（文字溢出）：
    - 问题：同一个意思，中文可能只要 4 个字（如“立即购买”），德语或俄语可能会变成一长串单词。如果按钮或导航栏写死了 width，文字就会爆出边界。
    - 应对：严禁写死容器的绝对宽度和高度。多使用 Flexbox、Grid 布局以及 min-width，并为可能溢出的长单词配置 word-break: break-word;。
    从右向左读的语种（RTL 适配）：
    - 问题：如果业务包含阿拉伯语（ar）、希伯来语（he），他们的阅读、滚动条、甚至返回按钮的方向都是从右到左的。
    - 应对：在 `<html>` 标签上动态标记 dir="rtl"。在编写 CSS 时，尽量使用 CSS 逻辑属性（如 margin-inline-start 代替 margin-left，text-align: start 代替 text-align: left），这样布局会自动根据方向镜像翻转。
    特殊语种的字体与排版：
    - 问题：某些语种（如泰语、阿拉伯语、印地语）的字母有很高的上下延伸部分（Ascenders/Descenders），如果 line-height（行高）设置得太低，字体的顶部和底部会被削掉。
    - 应对：针对不同语种，通过 CSS 选择器（如 :lang(th)）动态微调 font-family 和 line-height。

3. 用户体验与业务逻辑差异

    语言（Language）与地区（Locale）的混淆：
    - 问题：把“语言”和“国家”等同起来。例如，认为选了“加拿大”就一定是“英文”，忽略了加拿大有大量的法语人口；或者认为“中文”就只有“中国”，忽略了海外华人群体。
    - 应对：采用标准格式 [语言]-[地区]（如 en-US 美式英文, en-GB 英式英文, zh-CN 简体中文, zh-HK 繁体中文）。允许用户独立选择“我读取什么语言”和“我人在哪个国家/使用什么货币”。
    非文本要素的本地化（Localization）：
    - 问题：只翻译了字，但数字、日期、货币的格式不对，导致用户误解（例如：美国习惯 MM/DD/YYYY，欧洲习惯 DD/MM/YYYY）。
    - 应对：利用 JavaScript 原生的 Intl API（如 Intl.DateTimeFormat 和 Intl.NumberFormat）来自动根据当前 Locale 格式化日期、千分位、小数点和货币符号。
    多语言敏感度与文化禁忌：
    - 问题：某些地区的国旗、特殊政治敏感词、甚至配图中的手势或人物肤色，在不同国家可能会引发严重的法律或公关危机。
    - 应对：配合业务团队，在切换语言时，部分核心配图、Banner 甚至合规条款（如隐私政策、用户协议）也需要同步切换为对应国家/语种的版本。

4. SEO（搜索引擎优化）与路由

    如果你的网站依赖 Google 等搜索引擎带来流量，这一点是决定生死的前提：
    唯一可寻址的独立 URL：
    - 问题：如果通过 localStorage 动态切换文字，但网页的 URL（如 ://example.com）在任何语言下都一模一样，Google 的爬虫将只能抓取到你的默认语言，其他语言版本完全无法被搜索到。
    - 应对：必须让不同语言拥有独立的 URL 路径。首选子目录方案（如 /zh/about、/en/about），并在 HTML `<head>`中配置完整的 hreflang 标签，明确告诉搜索引擎各语言版本之间的映射关系。

## 使用 data- 属性的好处是什么？

1. 标准化自定义数据

- 合规性：在 HTML5 之前，开发者常在标签上随意编造非标准属性（如 my-id="..."），这不符合 HTML 规范。使用 data- 开头则将自定义属性标准化，不会破坏 HTML 语义，也能通过 W3C 验证。

2. 便于 JavaScript 操作

- dataset 对象访问：你可以通过元素的 .dataset 属性非常方便地读写这些数据。
- 命名转换：带有连字符的属性会自动转为驼峰命名。例如 data-user-id="123" 在 JS 中可通过 element.dataset.userId 获取。
- 兼容旧方法：对于老旧浏览器，也可以直接使用标准的 element.getAttribute('data-xxx') 和 element.setAttribute('data-xxx', value) 来获取或设置。

3. 支持 CSS 样式控制

- 属性选择器：你可以在 CSS 中直接通过 data-* 属性来选择元素并设置样式
- 配合 attr() 函数：甚至可以在 CSS 的 content 等属性中读取并显示这些数据。

4. 解耦数据与逻辑

- 保持结构干净：无需为了传一个 ID 或状态值而在 JS 代码里强行绑定复杂的全局变量或额外结构，直接把私有数据“贴”在对应的 HTML 元素上，实现结构与行为的更好结合。

## 如果把 HTML5 看作做一个开放平台，那它的构建模块有哪些？

1. 语义与结构模块 (Semantics)

这是平台的“骨架”。HTML5 废弃了过去到处都是 `<div>` 的混乱布局，引入了具备明确机器可读性的语义化标签。

- 核心组件：`<header>、<nav>、<article>、<section>、<aside>、<footer>`。
- 价值：不仅让代码结构更清晰，更重要的是为搜索引擎（SEO）和残障人士的屏幕阅读器（无障碍访问 Accessibility）提供了标准的数据结构解析。

2. 多媒体与图形模块 (Multimedia & Graphics)

这是平台的“多媒体引擎”。它彻底终结了对 Flash 等第三方插件的依赖，让浏览器原生具备了强大的视听与绘图能力。

- 音视频：`<video>` 和 `<audio>` 标签，支持原生的流媒体播放和控制。
- 2D 绘图：`<canvas>` API，允许通过 JavaScript 动态绘制图形、制作游戏和图表。
- 3D 图形：WebGL 技术，直接调用显卡硬件加速，在浏览器内实现复杂的 3D 渲染。
- 矢量图：内联 SVG 支持，保证图形在任何高清视网膜屏幕上都不会失真。

3. 客户端存储与离线模块 (Offline & Storage)

这是平台的“离线数据库”。它让 Web 应用能够像原生 App 一样，在没有网络的情况下依然可以运行和加载数据。

- Web Storage：包含 localStorage（持久存储）和 sessionStorage（会话级存储），存储容量相比传统的 Cookie 提升了数百倍（通常为 5MB+），且不随网络请求发送。
- IndexedDB：浏览器内置的客户端非关系型数据库（NoSQL），用于存储大量结构化数据。
- Service Workers：充当浏览器与网络之间的代理拦截器，是 PWA（渐进式 Web 应用） 的核心，负责离线缓存静态资源和实现离线访问。

4. 设备与硬件访问模块 (Device Access)

这是平台的“硬件接口”。它打破了浏览器与物理世界之间的隔阂，赋予了网页调用设备硬件的能力。

- 地理定位：Geolocation API，获取用户当前的 GPS 经纬度位置。
- 运动与方向：DeviceOrientation API，获取手机的陀螺仪、加速度计数据，用于实现摇一摇或重力感应游戏。
- 媒体捕获：getUserMedia API（WebRTC 的一部分），在用户授权后调用摄像头和麦克风。
- 现代扩展：随着开放平台的演进，现在还包含了 Web Bluetooth（蓝牙）和 WebUSB API。

5. 实时通信模块 (Connectivity)

这是平台的“高频神经系统”。它让网页告别了传统的“不断刷新/轮询”机制，实现了真正意义上的低延迟、双向实时数据传输。

- WebSocket：建立服务器与客户端之间的全双工、长连接通信通道，常用于在线聊天、股票K线、多人网页游戏。
- Server-Sent Events (SSE)：服务器向浏览器单向推送数据的轻量级通道。
- WebRTC：支持浏览器之间进行点对点（P2P）的语音、视频和数据实时全双工传输，无需绕过服务器中转。

6. 性能与并行计算模块 (Performance & Optimization)

这是平台的“加速器”。解决 JavaScript 单线程带来的卡顿问题，并提供高精度的性能监控。

- Web Workers：允许在后台线程中运行复杂的 JavaScript 计算任务（如解析大数据、图像处理），从而绝对不阻塞前台 UI 的滚动与交互。
- Performance API：提供高精度的网页加载、资源请求、页面渲染时间线数据，便于开发者进行精准的性能调优。

7. 三维视效与样式模块 (CSS3 联动)

作为平台的一部分，HTML5 往往与 CSS3 紧密绑定，提供原生的视觉特效能力。

- 核心组件：CSS3 3D 转换（Transforms）、过渡（Transitions）和动画（Animations）。
- 价值：无需复杂的 JS 动画库，即可利用 GPU 加速实现丝滑的页面翻转、阴影、渐变和流畅交互。

8. 安全与集成模块 (Device Integration & Security)

这是平台的“防火墙”。在赋予网页更多权力的同时，必须严格限制其越权行为。

- 拖放 API (Drag and Drop)：让网页元素甚至操作系统中的文件可以无缝拖拽进网页。
- History API：允许不刷新页面就能修改浏览器地址栏的 URL（现代前端路由 Vue Router / React Router 的基石）。
- 沙盒机制 (Iframe Sandbox)：对内嵌的第三方网页进行权限隔离，防止恶意脚本窃取主页面的敏感数据。

## 请描述 cookies、sessionStorage 和 localStorage 的区别

1. 为什么 Cookies 会自动参与通信？

Cookies 的诞生最初就是为了解决 HTTP 协议无状态 的问题。服务器需要一种机制来识别当前请求是谁发出的。

- 当你登录成功后，服务器会在响应头中加入 Set-Cookie: session_id=abc123。
- 之后，浏览器的每次点击、每次图片加载、每次 API 请求，都会默默带着这个 4KB 的小账本发送给服务器。因此，如果把无关的业务数据存入 Cookie，会极大地浪费用户的网络带宽。

2. SessionStorage 独有的“标签页隔离”

很多开发者容易误认为“只要浏览器没关，SessionStorage 就还在”。这是错误的。
SessionStorage 是绑定到特定的标签页（Tab）的：

- 如果你在 Chrome 中打开了两个一模一样的 百度 页面，它们各自的 SessionStorage 是互相独立的，修改 A 不会影响 B。
- 但如果你在当前标签页内刷新页面，或者通过页面内的链接跳转到同源新页面，SessionStorage 是会保留的。

3. 安全性差异（XSS 与 CSRF 攻击）

- Web Storage（Local/Session） 的数据很容易通过 JavaScript 读取（document.localStorage）。如果网站不幸遭遇了 XSS（跨站脚本攻击），黑客的恶意脚本可以轻而易举地把存放在里面的敏感信息（如 Token）全部偷走。
- Cookies 具备一个强大的安全防御属性：HttpOnly。如果在服务器端给 Cookie 加上这个标记，前端的 JavaScript 将完全无法读取它，这能有效防止登录凭证被 XSS 脚本窃取。

## 请解释 `<script>`、`<script async>` 和 `<script defer>` 的区别

1. 普通 `<script>`（同步阻塞）
    浏览器碰到它，必须停下手里所有的 HTML 解析工作，先去下载 JS，再执行 JS，全部搞定后才继续解析后面的 HTML。如果脚本很大，页面就会卡死白屏，几乎不再需要，除非是非常极端的场景（例如你需要在页面渲染之前，通过 JS 强行阻断并进行重定向或配置极其核心的全局变量）。
2. `<script async>`（异步下载，异步执行）
    下载是并行的，不耽误 HTML 解析。但是一旦下载完成，不管 HTML 解析到哪里，立刻强行插队执行，在执行期间 HTML 解析依旧会被卡住，适用于完全独立、不依赖其他脚本、也不被其他脚本依赖的第三方工具。
3. `<script defer>`（延迟执行，推迟执行）
    下载也是并行的，直到整个 HTML 完全解析完毕（在 DOMContentLoaded 事件触发之前），才会开始执行，适用于网站核心业务逻辑、组件交互代码、或者有前后依赖关系的脚本。

## 为什么通常推荐将 CSS `<link>` 放置在 `<head></head>` 之间，而将 JS `<script>` 放置在 `</body>` 之前？你知道有哪些例外吗？

为了让用户以最快速度看到没有排版错乱的网页（优化首屏体验），并防止脚本阻塞页面的渲染。

例外 1：使用 defer 或 async 属性的 JS 脚本（最普遍的例外）

现代开发中，我们完全可以把 JS 放心地写在 `<head>` 之间，前提是加上 defer 或 async 属性：

- 如果加上 `<script defer src="app.js">`，JS 的下载是并行的（不阻塞 HTML），且会自动等到 HTML 全部解析完后再执行。这完美解决了传统 JS 放头部带来的阻塞和找不到 DOM 的问题。现代脚手架（如 Vite、Webpack）打包出来的 HTML 默认就是把带 defer 的脚本放在 `<head>` 里。

例外 2：必须在首屏渲染前执行的“关键 JS”

有些脚本必须在用户看到任何画面之前生效，它们就必须放在 `<head>` 里：

- 移动端自适应方案（如旧版的 flexible.js）：需要根据手机屏幕宽度动态计算 `<html>` 的 font-size（Rem 布局）。如果放底部，页面会先以默认大小渲染，然后突然整体缩放闪烁。
- 主题色/暗黑模式切换：读取用户的系统偏好或 localStorage 决定今天显示白天还是黑夜模式。如果放底部，用户会先看到 1 秒钟亮瞎眼的白光，然后才变成黑夜模式。

例外 3：第三方统计与广告埋点脚本

- 如 Google Analytics（谷歌分析）、百度统计等。这些脚本通常使用 `<script async>`。为了尽可能早地捕捉到用户的每一次点击或流失（万一用户还没读到页面底部就关闭了网页），它们通常会被官方推荐放置在 `<head>` 的最顶部。

例外 4：关键 CSS（Critical CSS）的内联优化

- 在追求极致性能（如 Google Lighthouse 跑分）的超大型网站中，如果通过 `<link>` 异步下载一个几十 KB 的大 CSS 文件，首屏仍会有微小的延迟。
- 例外做法：将首屏首个画面（折叠屏上方 Visible Area）所必须的样式提取出来，做成内联样式直接写在 `<head>` 的 `<style>` 标签里，而把剩下的次要 CSS 通过 JS 异步延迟加载。

例外 5：现代首屏直出（SSR 服务端渲染）与 PWA

- 在使用 Next.js、Nuxt.js 或 PWA 离线技术时，首屏的 HTML 已经是服务端生成好的成品。此时脚本的放置位置完全由框架的同构激活（Hydration）机制决定，通常也会利用 module 或 defer 放在头部实现最高效的并行下载。

## 什么是渐进式渲染 (progressive rendering)？

渐进式渲染（Progressive Rendering）是现代 Web 性能优化的一种核心策略，它的核心思想是：不要让用户在一个完全空白的页面前死等，而是将网页内容分批次、由浅入深地呈现给用户。

1. 骨架屏与占位符（Skeleton Screens）

- 做法：在真实的数据、图片和文字从服务器下载完成之前，先用灰色的线条、几何方块或淡入淡出的动画拼凑出一个“网页的大致轮廓”。
- 价值：它在感知性能（Perceived Performance）上非常强大。研究表明，看到骨架屏的用户会觉得网站加载速度更快，相比单纯的转圈圈加载动画（Spinner），骨架屏能大大降低用户的焦虑感。

2. 关键 CSS 提前注入（Critical CSS）

- 做法：将用户一眼看过去最先看到的画面（首屏、折叠线以上的区域，即 Above the Fold）所需的 CSS 样式提取出来，直接内联（Inline）写在 HTML 的 `<head>` 标签内的 `<style>` 中。而剩下的非首屏 CSS 则通过异步方式延迟下载。
- 价值：浏览器拿到 HTML 就能立刻渲染出漂亮的首页，绝对不会因为下载几百 KB 的完整样式表而导致首屏白屏。

3. 图片渐进式加载（Progressive Images / LQIP）

- 渐进式 JPEG（Progressive JPEG）：这种图片格式在下载时，会先显示一张模糊的低分辨率全图，随着数据下载，图片逐渐变清晰，而不是像传统 Baseline JPEG 那样从上到下一行一行地硬生生刷出来。
- 低画质图片占位（LQIP, Low Quality Image Placeholders）：先加载一张只有几百字节、高模糊的缩略图（或使用纯色块、BlurHash），当真实的高清大图下载完成后，再平滑淡入切换。

4. HTML 流式传输（HTML Streaming）

- 做法：现代服务端渲染（SSR）框架（如 React 18+ 的 Streaming SSR，基于 Node.js Stream）允许服务器不需要等整个页面的数据全部查完。服务器可以先生成并发送页面的 Header 和基本框架（Layout），此时用户的浏览器就已经开始解析和渲染了。当后端慢速的数据库查出核心内容后，再通过同一个 HTTP 连接把剩下的 HTML “流”式推送给浏览器。

5. 组件懒加载与分批激活（Lazy Loading & Selective Hydration）

- 做法：在 React / Vue 的同构（SSR）应用中，传统的做法是整个页面的 JS 下载完后一次性激活（Hydrate）全页。而渐进式激活允许优先下载和激活用户正在交互的核心组件（如顶部的导航或评论框），而底部的次要组件等滚动到可视区域时再进行加载和激活。

## 简单介绍 requestIdleCallback 及使用场景

requestIdleCallback用于在浏览器“空闲”时段执行低优先级的后台任务。 它的核心思想是：利用动画、输入响应等高优先级任务执行完毕后的剩余时间，去处理一些非紧急的琐碎工作，从而避免阻塞主线程，保证页面交互的流畅度（如防止打字卡顿、动画掉帧）

由于它只能在“有空”的时候执行，因此它只适合非紧急、低优先级、且可以被拆分的任务：

1. 发送非关键性埋点与分析数据
在用户浏览页面或关闭页面时，通常需要向后端发送各种统计、打字行为、性能监控等埋点数据。这些任务完全不影响用户当下的操作，非常适合放在空闲时批量发送。
2. 数据的预加载与预解析
当页面处于静止状态时，可以利用空闲时间去预先下载用户可能点击的下一页数据，或者预先解析一部分即将用到的复杂数据。
3. 创建/拆分低优先级的 DOM 节点
例如，点击一个按钮需要渲染一个拥有上千条数据的复杂下拉列表。为了防止页面瞬间卡死，可以将数据拆分为多批，利用 requestIdleCallback 每次渲染一小部分，实现增量渲染。
4. 缓存清理与垃圾回收
在主线程空闲时，清理前端本地过期的 localStorage、IndexedDB 缓存，或者重置某些不需要的变量状态。

## 什么是重排重绘，如何减少重拍重绘

重排必定引发重绘，但重绘不一定会引发重排，重排的性能开销远大于重绘。

- 重排（Reflow / Layout）：计算几何结构。
当页面中元素的几何属性（如尺寸、位置、隐藏显示等）发生改变时，浏览器需要重新计算该元素以及受其影响的其他元素在屏幕上的确切大小和位置。这是一个非常消耗性能的“全局性”操作。
- 重绘（Repaint）：填充像素颜色。
当元素的外观样式（如背景颜色、字体颜色、边框颜色、阴影等）发生改变，但不影响其几何布局时，浏览器不需要重新计算位置，只需要重新像素绘制这部分元素。

如何减少重排和重绘？

1. 批量修改样式（集中操作）
避免通过 JS 逐行修改样式，这会导致浏览器频繁触发重排，建议合并为一次性操作

2. 离线操作 DOM
如果需要对 DOM 节点进行多次复杂的增删改操作，先让该节点“离线”，操作完成后再放回页面中。

    - 使用文档碎片（DocumentFragment）： 在内存中构建好完整的 DOM 树，最后一次性插入页面。
    - 先隐藏再显示： 使用 display: none 将元素隐藏（触发一次重排），进行 100 次操作后，再恢复 display: block（触发一次重排），这样中间的 100 次操作都不会引发页面抖动。

3. 避免频繁读取“布局信息”
    当你在 JS 中读取某些特定属性时，为了保证拿到最新、最精准的值，浏览器会强制刷新队列并立即进行一次重排（俗称“强同步布局”）。

    - 常见的“雷区”属性：offsetTop/offsetLeft、offsetWidth/offsetHeight、scrollTop/scrollLeft、clientWidth/clientHeight、getComputedStyle()。
    - 优化方案（读写分离）： 不要把读取和修改混在一起。javascript

    // 差的做法：每次循环都读取 offsetWidth 导致反复重排（圣杯布局死循环）

    ```
    for (let i = 0; i < divs.length; i++) {
        divs[i].style.width = box.offsetWidth + 'px'; 
    }
    ```

    //  好的做法：先用变量缓存起来

    ```
    const targetWidth = box.offsetWidth;
    for (let i = 0; i < divs.length; i++) {
        divs[i].style.width = targetWidth + 'px';
    }
    ```

4. 善用 CSS3 硬件加速（合成层）
有些 CSS 属性可以直接绕过重排和重绘，由 GPU（显卡）直接进行“合成”处理（Composite），性能极高。

尽量使用 transform 代替 top/left 来实现动画位移。
尽量使用 opacity 代替 display/visibility 来实现渐隐渐现。
对经常变换的复杂动画元素，可以使用 will-change: transform，提前告诉浏览器将其提升为独立的合成层。
  
5. 降低受影响的“触发布局树”范围

脱离文档流：将复杂的动画元素设置为 position: absolute 或 fixed。这样它的重排只会在局部进行，不会带动整个页面的其他大面积元素跟着一起重排。

## 什么是 Data URL

Data URL（数据链接） 是一种将小文件直接嵌入到代码中的统一资源定位符（URL）方案，通常情况下，我们在网页中引用图片、音频或字体时，会使用指向服务器路径的普通 URL，而 Data URL 则允许你不通过额外的网络请求，直接把文件内容以字符串（通常是 Base64 编码）的形式，直接写在 HTML、CSS 或 JavaScript 代码中

1. 小图标/小图片的直接嵌入（CSS Sprites 的现代替代方案）
在 CSS 中，你可以直接把小背景图或 Logo 转成 Data URL 填入 url() 中。
2. 减少 HTTP 网络请求（提升小文件加载性能）
如果页面上有 20 个几百字节的小图标，按传统方式浏览器需要发起 20次 HTTP 请求，而直接嵌入到 HTML/CSS 中，可以将请求数直接降为 0。
3. 前端预览本地文件
当用户在网页中通过 `<input type="file">` 上传图片时，前端可以使用 FileReader.readAsDataURL() API 瞬间将图片转为 Data URL，并赋值给 `<img>` 标签的 src 属性，实现无服务器参与的本地图片秒级预览。
4. 移动端/邮件 HTML 离线查看
在一些需要完全离线查看的单文件 HTML，或者无法外链资源的电子邮件中，所有图片和资产都必须使用 Data URL 嵌入。

值得注意的是，要应对“浏览器缓存”导致的跨域失败，在实际工程中，你可能会遇到一个诡异的 Bug：图片直接用 `<img>` 标签展示没问题，但一旦放到 Canvas 里设置了 crossOrigin 就会报跨域错误（甚至报 CORS missing），它直接从本地缓存中读取了之前那张不带 CORS 头的图片，导致判定跨域失败，解决方案就是给地址加上一个随机参数或时间戳参数

请谨慎使用此类代码。

## prefetch 与 preload 的区别是什么

preload 用于声明当前页面在加载和渲染过程中，必须、马上、高优先级要用到的资源

- 核心原理： 浏览器通常在解析 HTML 时，遇到深入嵌套的资源（如 CSS 里引用的字体文件、JS 动态加载的次级脚本）会发现得比较晚。使用 preload 可以让浏览器跳过这些链路，在刚拿到 HTML 时就并行、最高优先级去下载它们，绝不耽误当前页面的首屏渲染。
- 语法格式： 必须使用 as 属性指定资源类型（如 style, script, font, image），以便浏览器为其分配合适的下载优先级和缓存策略。

prefetch 用于声明未来（下一个页面或下一阶段交互）可能会用到的资源

- 核心原理： 它的优先级是最低（Idle / Lowest）的。浏览器会等到当前页面完全加载完毕、主线程彻底空闲下来之后，才利用剩余的带宽偷偷去下载这些资源，并把它们缓存在本地（Disk Cache）。
- 使用场景： 当用户登录了电商首页，你猜测他下一步大概率会点击“购物车”或“商品详情页”，就可以利用 prefetch 提前把购物车页面的打包 JS 和大图下载好。这样用户一旦点击跳转，新页面就能瞬间秒开。

应用：

1. 路由懒加载（Route-based Prefetch）： 当你使用 Next.js 或 Nuxt 时，只要页面上出现了一个 `<Link href="/about">` 标签，只要这个链接滚入到了用户的可见视口内，框架就会自动触发对 /about 页面组件的 prefetch。这正是现代单页应用实现“丝滑秒开”的终极秘密。
2. 异步组件生成： 打包工具（如 Vite / Webpack）在把代码拆分成多个小 chunk 时，会自动把首屏必需的动态提取项通过 preload 注入 HTML 头，把低优先级的按需加载项通过 prefetch 处理，完美平衡了带宽和响应速度。

## 当 cookie 没有设置 maxage 时，cookie 会存在多久

如果同时也没有设置 expires，只要用户关闭了当前浏览器（所有的标签页和主程序窗口全部关闭），这个 Cookie 就会被浏览器从内存中自动清除并彻底销毁，有以下两个特殊情况：

1. 浏览器的“活动继续”/“恢复上次打开的页面”功能：
像 Google Chrome、Microsoft Edge 以及 macOS 的 Safari，默认或可选开启“启动时恢复上一次关闭时的页面”功能。如果你勾选了该功能，即使你彻底关闭了浏览器再重新打开，浏览器会完美还原上一次的内存状态，此时原有的会话 Cookie 依然会神奇地存在，用户不会因此被迫退出登录。
2. 手机端（移动端）浏览器：
在 iOS 和 Android 手机上，用户按下 Home 键或往上划掉 App，通常只是把浏览器送入后台或挂起，并不会真正杀死浏览器进程。即使在任务管理器里手动“杀掉”浏览器，手机系统为了优化体验，也经常会保留表单和会话 Cookie。因此在手机端，会话 Cookie 的存活时间往往比 PC 端长得多。

## 什么是层叠上下文 (stacking context)

层叠上下文（Stacking Context）是 HTML 元素在网页三维空间中沿着 Z 轴（垂直于屏幕的方向） 排列的虚拟分层概念。它决定了当多个元素在屏幕上发生重叠时，谁在上面、谁在下面

核心运行机制：在同一个层叠上下文中，元素的渲染顺序遵循层叠黄金准则。从屏幕最底层（远离用户）到最顶层（靠近用户）的排列顺序如下：

1. 背景和边框：形成该上下文的元素的根背景。
2. 负 Z-Index：z-index 值为负数的子层叠上下文。
3. 块级流：常规流中的非定位块级子元素。
4. 浮动流：非定位的浮动子元素。
5. 内联流：常规流中的内联（文本）子元素。
6. Z-Index: 0 / Auto：定位了但 z-index 为 0 或 auto 的子元素。
7. 正 Z-Index：z-index 值为正数的子层叠上下文。
  
为什么你的 z-index 经常失效？

网页开发者最常遇到的“z-index 不起作用”问题，通常是因为拼爹效应（层叠上下文的独立性）：

- 独立子王国：每个层叠上下文都是独立的。子元素的层叠顺序完全受制于父级层叠上下文。
- 无法超越父级：如果父元素 A 的层叠顺序低于父元素 B，那么即使 A 的子元素设置了 z-index: 99999，它也永远被 B 压在下面。

3. 如何触发（创建）层叠上下文？

一个元素不会无缘无故变成“层叠上下文”，它需要被特定的 CSS 属性“激活”。以下是几种最常见的触发方式：

- 文档根元素：网页的 `<html>` 标签天然是一个根层叠上下文。
- 传统定位组合：设置了 ```position: relative / absolute / fixed / sticky 且 z-index``` 的值不是 auto 的元素。
- 现代布局属性：
  - Flex 或 Grid 容器的子元素，且 z-index 不是 auto。
  - 元素的 opacity 属性值小于 1。
  - 元素的 transform、filter、perspective、clip-path 属性值不是 none。
  - 元素的 will-change 属性指定了上述任意属性。

## 什么是事件冒泡和事件捕获

1. 事件捕获（Event Capturing）

- 方向：从外向内（由表及里）。
- 过程：当点击 `<button>` 时，浏览器会从最外层的顶级祖先元素（`window -> document -> <html> -> <body>`）开始，一层层向下寻找真正被点击的那个元素。
- 特点：在事件到达目标元素之前，父级元素会先“捕获”到这个事件。

2. 事件冒泡（Event Bubbling）

- 方向：从内向外（由浅入深，像水底的气泡浮出水面）。
- 过程：事件在到达目标元素（`<button>`）并触发后，不会立刻结束，而是会沿着原路反向向上传播，依次触发父级、祖父级直到 window 上的同名事件。
- 特点：现代浏览器默认所有的事件监听器都运行在冒泡阶段。

## 浏览器中 cookie 有哪些字段

- Name（名称）：Cookie 的键名（Key），在同一个作用域下必须唯一。
- Value（值）：Cookie 存储的文本数据（通常需要进行 URL 编码，以防包含分号或空格等特殊字符）。
- Expires（过期时间）：指定 Cookie 失效的具体格林威治时间（GMT/UTC）。
- Max-Age（最大生存周期）：指定 Cookie 在多少秒后失效（例如 Max-Age=3600 表示 1 小时后过期），Max-Age 的优先级高于 Expires。如果两者都没设置，则该 Cookie 为会话 Cookie（Session Cookie），会在浏览器关闭时被自动清除。
- Domain（域名）：指定哪些域名或子域名可以访问该 Cookie，如果未显式指定，默认只对当前主机名（Host）有效，且不包含子域名。
- Path（路径）：限制只有匹配该路径的 URL 才能携带该 Cookie，通常默认设为 /，表示整站通用。
- Secure（安全标志）：一个布尔标记（无值），设置后，该 Cookie 只能通过 HTTPS 加密协议传输，在非加密的 HTTP 请求中不会被浏览器发送，以此防止中间人窃听（MITM）。
- HttpOnly（仅限 HTTP 传输）：一个布尔标记，设置后，前端的 JavaScript 代码（如 document.cookie）将完全无法读取或修改该 Cookie。这是防御 XSS（跨站脚本攻击） 窃取用户 Session Token 的最核心手段。
- SameSite（跨站限制）：用于控制 Cookie 在跨站（Cross-Site）请求时是否随请求发送，是防御 CSRF（跨站请求伪造）的主力字段。它

## DOM 中 Element 与 Node 有何区别

1. 什么是 Node（节点）？
Node 是 DOM 树中最基本的组成单元。整个网页上的任何一个部分，在 DOM 眼里都是一个节点。
常见的节点类型（可以通过 node.nodeType 查看）包括：

- 文本节点（Text Node，nodeType === 3）：标签内的文字、甚至连标签之间的换行和空格都会被浏览器当成文本节点。
- 注释节点（Comment Node，nodeType === 8）：HTML 中的 <!-- 注释 -->。
- 文档节点（Document Node，nodeType === 9）：最顶层的 window.document。

2. 什么是 Element（元素）？

Element 是 Node 的一种特定子类型。它专指具有 HTML 标签形式的节点，比如 `<div>、<p>、<a>` 等。

## SameSite Cookie 有哪些值，是如何预防 CSRF 攻击的

1. Strict：极其严格。完全禁止第三方请求携带该 Cookie，只有在当前地址栏的域名和请求域名一致时才会发送。
2. Lax：现代浏览器默认值。允许在用户进行普通的跨站顶级导航（例如点击链接 `<a>` 跳转）时携带，但通过 `AJAX、<img>、<iframe>` 等触发的第三方请求依然不带。
3. None：完全不限制。任何跨站请求都会携带该 Cookie，但要求必须同时设置 Secure 属性（即只能在 HTTPS 下生效）。

安全要求极高的核心业务（如金融、支付、修改密码），应当采用 SameSite=Lax + CSRF Token 验证（或双重 Cookie 校验） 的双保险方案。

## 浏览器中监听事件函数 addEventListener 第三个参数有那些值

1. capture (Boolean)

- 作用：功能等同于上面的布尔值。
- 取值：true 表示在捕获阶段触发，false（默认）表示在冒泡阶段触发。

2. once (Boolean)

- 作用：控制该事件监听器是否只触发一次。
- 取值：如果设为 true，当事件第一次触发并执行完回调后，浏览器会全自动将其销毁（自动执行 removeEventListener）。这在处理“一次性点击”、“初始化激活”等场景时非常实用，免去了手动解绑的麻烦。

3. passive (Boolean)

- 作用：显式声明该监听器永远不会调用 preventDefault() 来阻止默认行为。
- true：告知浏览器“我绝对不会阻止默认滚动”。现代浏览器在移动端的 touchstart、touchmove 和 wheel 事件上，默认会将其设为 true。这样浏览器就不需要等待你的 JS 脚本执行完毕，就可以直接丝滑地滚动页面，极大地提升了滚动性能和帧率。
- false：允许在事件内部调用 preventDefault()。

4. signal (AbortSignal)

- 作用：允许你通过现代的 AbortController 来一键批量取消、联动卸载事件监听器。
- 取值：传入一个 AbortSignal 对象。当你调用控制器的 abort() 方法时，绑定了该信号的事件监听器会被立刻自动移除。

## 浏览器中 Frame 与 Event Loop 的关系是什么

在浏览器中，Frame（渲染帧）与 Event Loop（事件循环）是“嵌套与协同”的关系。简而言之：渲染帧是事件循环中一个可选的、高优先级的子阶段。事件循环（Event Loop）不停地循环执行任务，而在大部分屏幕刷新率（如 60Hz，约 16.7ms 一帧）的背景下，事件循环在特定周期的尾部，会专门拨出一部分时间来执行 Frame 渲染流，以确保页面画面得以更新。 

### 一、 经典的一帧（Frame）全生命周期

1. Task（宏任务）：执行事件循环队列中的一个常规宏任务（如：用户的 click 事件、setTimeout 回调）。
2. Microtask（微任务）：清空当前所有的微任务队列（如：Promise.then、MutationObserver），直到队列为空。
3. 【进入渲染帧阶段 (Begin Frame)】：浏览器根据屏幕刷新率和性能判断，如果到了该刷新画面的时候，便会切入渲染流程：

- requestAnimationFrame (rAF)：首先执行通过 rAF 注册的 JS 回调。这是在修改 DOM 样式并保证不掉帧的最佳时机。
- Style（样式计算）：根据 CSS 规则，计算每个 DOM 元素的最终样式。
- Layout（布局/回流）：确定页面上所有元素的几何位置和大小（几何计算）。
- Paint（绘制/重绘）：将元素转化为屏幕上的像素点（创建绘制记录，由合成线程接管）。

4. requestIdleCallback (rIC)：如果上述所有步骤执行完，这一帧 16.7ms 还没有用完，浏览器会在剩余的空闲时间里，去执行低优先级的 requestIdleCallback 任务

### 二、 核心关系与四大运行金律

1. 渲染（Frame）并不是每轮事件循环都会发生的

事件循环的 Tick 速度极快（可能只需不到 1ms 就能跑完一轮宏任务+微任务）。但是，显示器的物理刷新率是固定的（例如 60Hz 对应 16.7ms，120Hz 对应 8.3ms）。

- 策略：如果事件循环跑得太快，离上一次渲染还不到 16.7ms，事件循环会直接跳过当前的渲染阶段，继续疯狂执行下一个 Task。
- 极端情况：如果你的代码里死循环执行微任务（如无限递归 Promise.then），由于事件循环被死死卡在清空微任务的步骤中，永远无法推进到后面的“渲染帧阶段”，导致浏览器彻底画面假死。

2. 定时器 setTimeout 与渲染帧完全不同步

很多人误以为 setTimeout(fn, 16.7) 就能完美契合 60Hz 刷新率，这是错误的。

- setTimeout 仅仅是将任务扔进事件循环的宏任务队列，它何时执行，取决于前面有没有其他耗时任务排队。
- 如果 setTimeout 在这一帧的 Layout 之后才被执行，那它修改的样式只能等到下一帧才会渲染，从而导致视觉上的“掉帧”或卡顿。

3. requestAnimationFrame（rAF）是事件循环给渲染留的专用后门

rAF 的回调函数被硬性规定在渲染帧（Begin Frame）的第一步执行。这意味着：

- 只要你把修改样式的 JS 代码写在 rAF 里，浏览器就能保证你的修改绝对会在接下来的 Style / Layout 中被立刻计算，并在这一帧毫无延迟地刷新到屏幕上。

4. 微任务（Microtask）是一座桥梁

无论是常规的 Task 内部，还是在 rAF 的回调函数内部，只要产生了微任务（如 Promise），事件循环都会在当前子阶段结束前，立刻把这批微任务清空。例如，rAF 里产生了一个 Promise，在进入 Style 样式计算之前，这个 Promise 的 .then 就会被率先一口气执行完。
