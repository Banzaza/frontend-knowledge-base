# JavaScript

## 说说Javascript中的数据类型？区别？

1. 原始类型（Primitive Types，共 7 种）直接存储值本身，栈内存（Stack），不可变（修改值其实是创建了新值），值传递/拷贝副本：赋值给新变量时，会独立复制一份新值，比较的是值是否相等（===），用typeof 检测返回对应类型

- String：字符串（如 'hello'）
- Number：数字（包括整数和浮点数，如 42, 3.14，以及 NaN, Infinity）
- Boolean：布尔值（true 或 false）
- Undefined：未定义（声明了变量但未赋值时，默认值为 undefined）
- Null：空值（表示一个空对象指针或无值）
- Symbol：ES6 新增，表示独一无二的值
- BigInt：ES11 新增，用于表示任意大的整数

2. 引用类型（Reference Types / Object），存储的是指向堆内存的内存地址（指针），对象本身存放在堆内存（Heap），而指向它的地址存放在栈内存中，可变（可以动态添加、修改或删除属性），引用传递/共享地址：赋值给新变量时，拷贝的是地址，两个变量指向同一个堆内存对象，比较的是内存地址是否相同（而不是内容是否一样），除了函数返回 'function' 外，普通对象、数组、Date 等都返回 'object'

- Object：复杂结构，包括标准对象 {}、数组 Array、函数 Function、日期 Date、正则 RegExp 等。

## Javscript数组的常用方法有哪些？

一、 会改变原数组的方法（Mutation Methods）

- push() / pop()：在数组末尾添加一个或多个元素（返回新长度）/ 删除最后一个元素（返回被删除的元素）。
- unshift() / shift()：在数组开头添加一个或多个元素（返回新长度）/ 删除第一个元素（返回被删除的元素）。
- splice(start, deleteCount, item1, ...)：万能修改器。从指定索引开始，删除、替换或插入新元素，返回由被删除元素组成的数组。
- sort(compareFn)：对数组元素进行原地排序。注意：默认按字符串 Unicode 码点排序，数字排序需传入 (a, b) => a - b。
- reverse()：将数组中的元素位置颠倒。
- fill(value, start, end)：用一个固定值填充数组中从起始索引到终止索引内的全部元素。

二、 不会改变原数组的方法（Non-Mutation Methods）

1. 遍历与转换（高阶函数）

- forEach(fn)：遍历数组执行回调函数，无返回值（返回 undefined），无法使用 break 中断。
- map(fn)：遍历并映射，返回一个由每次回调返回值组成的新数组（长度与原数组一致）。
- filter(fn)：过滤元素，返回所有使回调函数返回 true 的元素组成的新数组。
- reduce(fn, initialValue)：累加器，从左到右将数组元素汇总为单个值（如求和、数组扁平化、统计次数等）。

2. 查找与判断

- find(fn) / findIndex(fn)：返回第一个满足条件的元素本身 / 它的索引（找不到分别返回 undefined 和 -1）。
- includes(value)：判断数组是否包含某个指定的值，返回布尔值 true 或 false（支持识别 NaN）。
- indexOf(value) / lastIndexOf(value)：返回指定元素在数组中首次 / 最后一次出现的索引，不存在则返回 -1。
- some(fn) / every(fn)：判断数组中是否至少有一个 / 所有元素都满足条件，返回布尔值（支持短路机制）。

3. 截取、合并与转字符串

- slice(start, end)：浅拷贝并截取数组的一部分，返回新数组（包头不包尾）。
- concat(arr1, ...)：合并两个或多个数组，返回一个新数组。
- join(separator)：将数组的所有元素连接成一个字符串，可指定分隔符（默认逗号）。
- flat(depth)：按照可指定的深度递归遍历数组，将所有子数组元素合并为一个新数组（常用于数组扁平化，如 arr.flat(Infinity)）。

## Javascript字符串的常用方法有哪些？

JavaScript 中的字符串是不可变的，所以所有的字符串方法都不会修改原字符串，只是返回一个新的字符串或对应的结果。

- includes(searchString, position)：判断字符串是否包含指定的子字符串，返回布尔值 true 或 false（最常用）。
- startsWith(searchString) / endsWith(searchString)：判断字符串是否以指定的子字符串开头或结尾，返回布尔值。
- indexOf(searchValue) / lastIndexOf(searchValue)：返回指定子字符串首次 / 最后一次出现的索引，找不到则返回 -1。
- search(regexp)：检索与正则表达式相匹配的值，返回第一个匹配项的索引，未找到返回 -1。
- slice(start, end)：提取字符串的某个部分，返回一个新字符串（包头不包尾）。支持传入负数（表示从字符串末尾倒数计算，最推荐使用的截取方法）。
- substring(start, end)：功能与 slice() 类似，但不支持负数（负数会被当作 0 处理）。
- charAt(index) / at(index)：返回指定索引位置的字符。ES2022 新增的 at() 支持负数索引（如 str.at(-1) 获取最后一个字符）。
- replace(pattern, replacement)：在字符串中查找匹配的子串（可以是字符串或正则），并替换为新子串。注意：传入普通字符串时，只替换第一个匹配项。
- replaceAll(pattern, replacement)：ES2021 新增，替换所有匹配的子串（若传入正则表达式，必须带有全局标志 /g）。
- split(separator, limit)：使用指定的分隔符将一个字符串分割成子字符串数组（例如 str.split('') 可将字符串转为字符数组）。
- toUpperCase() / toLowerCase()：将字符串全部转换为大写或小写（常用于忽略大小写的搜索或比较）。
- trim()：去除字符串两端的空白字符（空格、制表符、换行符等）。
- trimStart() / trimEnd()：仅去除字符串开头或结尾的空白字符。
- concat(str1, str2, ...)：连接两个或多个字符串，返回新字符串（实际开发中通常直接用 + 或模板字符串 `${a}${b}` 替代）。
- padStart(targetLength, padString) / padEnd(targetLength, padString)：用另一个字符串填充当前字符串的头部或尾部，直到达到指定的目标长度（常用于日期时间补零，如 '5'.padStart(2, '0') 得到 '05'）。
- repeat(count)：构造并返回一个新字符串，包含被连接在一起的指定数量的原字符串副本。

## 谈谈 Javascript 中的类型转换机制

JavaScript 是一种弱类型语言，其类型转换机制分为显式类型转换（强制转换）和隐式类型转换（自动转换），且目标类型最终只有三种：数字（Number）、字符串（String）和布尔值（Boolean）。

## == 和 === 区别，分别在什么情况使用

==会在比较前进行隐式类型转换，而 ===（严格相等）不会进行类型转换，要求值和类型都必须完全一致，在开发中，除了判空之外，都应该使用 ===

## 深拷贝浅拷贝的区别？如何实现一个深拷贝？如何解决深拷贝问题中的循环引用

浅拷贝只复制引用类型的引用，和原数据依旧使用同一份堆内存的数据，深拷贝则会在堆内存中复制一份引用类型数据的值，修改新对象不会影响原对象。

1. 现代原生方案：structuredClone()（日常开发首选），浏览器和 Node.js（17+）已内置原生全局方法，性能优秀且支持多种复杂类型（Date、RegExp、Map、Set 等）以及自动处理循环引用，不支持拷贝函数（Function）、DOM 节点和 Symbol 属性（遇到会报错）。

2. 简易黑科技：JSON.parse(JSON.stringify())，会忽略 undefined、函数和 Symbol；会把 Date 变成字符串；把 RegExp 变成空对象 {}；遇到 NaN/Infinity 会变成 null；遇到循环引用会直接报错。

3. 手写完整版深拷贝

如何解决深拷贝中的“循环引用”问题？

1. 什么是循环引用？

当一个对象的属性直接或间接地指向它自身时，就形成了循环引用，如果深拷贝函数没有做防备，递归遍历时就会无限进入死循环，最终撑爆调用栈，抛出栈溢出错误。

2. 解决原理：哈希表缓存（记录拷贝历史），在递归外部创建一个缓存容器（存储 原对象 -> 拷贝后的新对象 的映射关系），每次准备克隆一个对象前，先查缓存，如果这个原对象已经克隆过了，说明遇到了循环引用，直接从账本里取出对应的新对象返回，不再继续往下递归，如果没克隆过，立刻把 { 原对象: 刚创建的空新对象 } 登记进账本，然后再去递归拷贝它的子属性（注意：必须先登记再递归，否则子属性引用自身时账本里还没有记录）。

3. 为什么必须用 WeakMap 而不是普通 Map 或 {}？不能用普通对象是因为普通对象的键只能是字符串或 Symbol，如果把对象作为键，它会被隐式转换成 "[object Object]"，导致所有对象覆盖同一个键，WeakMap 的键必须是对象，且持有的是弱引用。一旦深拷贝函数执行完毕，如果外部不再引用这些临时对象，垃圾回收器（GC）可以自动回收内存，彻底避免内存泄漏。

## 说说你对作用域链的理解

作用域链是 JS 引擎用来查找变量的单向链式机制，当代码访问某个变量时，引擎会先在当前执行上下文中寻找，如果找不到，就会沿着外层作用域逐级向上查找，直到全局作用域为止。JS函数的作用域在它声明的那一刻就已经决定了，而不是在“调用”时决定。

作用域链是实现闭包的基础：

- 当外层函数 outer 返回了内层函数 inner 时，虽然 outer 执行完毕并从调用栈弹出，但因为 inner 的作用域链中依然保留着对 outer 作用域的引用，垃圾回收器不会销毁 outer 中被 inner 引用的变量。
- 无论 inner 在哪执行，它依旧能顺着这条作用域链读写 outer 中的变量。

## JavaScript原型，原型链 ? 有什么特点？

原型（Prototype）是 JavaScript 实现对象属性共享与继承的基石，本质上是一个普通对象；原型链（Prototype Chain）则是对象之间通过隐式原型指针（[[Prototype]] / __proto__）串联起来的单向查找链条，终点是 null。

一、 原型的核心“三角关系”

在 JavaScript 中，几乎所有对象都有原型，理解以下三个核心属性就能打通整个原型机制：

1. prototype（显式原型）：只有函数（Function）才拥有的属性（箭头函数除外）。它指向一个对象，这个对象包含了所有实例共享的属性和方法。
2. __proto__（隐式原型）：所有对象（包括函数和实例）都拥有的内部指针（标准规范为 [[Prototype]]，现代开发推荐使用 Object.getPrototypeOf() 访问）。它指向创建该对象的构造函数的 prototype。
3. constructor（构造器）：原型对象（prototype）上默认自带的属性，指回构造函数本身。

二、 什么是原型链？（查找机制）

当你访问一个对象的属性或方法（例如 p1.toString()）时，JS 引擎会按照以下路径进行查找：

1. 先查自身：在 p1 自身属性中找，找到直接返回。
2. 沿链向上：没找到，就顺着 p1.__proto__ 去 Person.prototype 中找（找到了 sayHi）。
3. 继续向上：还没找到，就顺着 Person.prototype.__proto__ 去 Object.prototype 中找（找到了 toString）。
4. 抵达终点：如果到了 Object.prototype.__proto__（即 null）依然没找到，查找结束，返回 undefined（如果是调用不存在的方法则抛出 TypeError）。

三、 原型与原型链的五大核心特点

1. 属性与方法的共享性（节省内存）

- 将公共方法定义在构造函数的 prototype 上，所有通过 new 创建的实例都能直接调用，而不需要在每个实例的内存中重复创建一份函数副本，极大节省了堆内存空间。

2. 就近原则（属性遮蔽 / Property Shadowing）

- 如果实例自身添加了与原型上同名的属性（如 p1.sayHi = ...），访问时会优先命中实例自身的属性，从而“遮蔽”原型上的属性，不会修改原型上的原始值。

3. 动态性

- 原型对象是动态可变的。即使在实例化对象创建之后，再向构造函数的 prototype 添加新方法，之前创建的实例依然能够通过原型链访问到这个新方法（因为它们共享同一个指针引用）。

4. 引用类型共享的副作用（双刃剑）

- 如果在原型上定义了引用类型的属性（例如 Person.prototype.hobbies = ['reading']），某一个实例通过 p1.hobbies.push('coding') 修改它时，所有其他实例的 hobbies 都会跟着被污染。因此，数据属性通常定义在构造函数内部（this.hobbies = []），只有方法才放在原型上。

5. 所有函数的终极归宿（鸡生蛋问题）

- 所有函数（包括 Object、Array、Function 自己）都是 Function 的实例，因此 Function.__proto__ === Function.prototype（为 true），而 Function.prototype.__proto__ === Object.prototype。这意味着函数也是对象，最终依然汇入 Object.prototype。

ES6 引入的 class、extends、super 关键字，在底层完全是基于原型和原型链实现的“语法糖”

## Javascript如何实现继承？解释其原理

在 JavaScript 中，继承的本质是让子类实例能够同时拥有父类实例的属性，并通过原型链访问父类原型上的共享方法。现代开发中最标准的是 ES6 的 class 语法糖（extends + super），而在 ES5 时代最完美的底层实现方案是“寄生组合式继承”。

在 ES6 之前，JavaScript 经历了多种继承方案的演进，最终定型为寄生组合式继承（这也是 Babel 编译 ES6 class 时采用的核心思路）。

```javascript
function Parent(name) {
  this.name = name;
}
Parent.prototype.sayName = function() {
  console.log(this.name);
};

function Child(name, age) {
  // 1. 借用构造函数：将父类实例属性绑定到子类实例上（解决引用属性共享问题）
  Parent.call(this, name); 
  this.age = age;
}

// 2. 原型链继承：创建一个以 Parent.prototype 为原型的空对象，赋给 Child.prototype
Child.prototype = Object.create(Parent.prototype);

// 3. 修复 constructor 指向（否则会指向 Parent）
Child.prototype.constructor = Child;

Child.prototype.sayAge = function() {
  console.log(this.age);
};
```

## 谈谈this对象的理解

this 是执行上下文中的一个动态指针，它是由函数被调用的调用位置动态决定的（唯一的例外是 ES6 箭头函数，它在定义时就继承了外层的 this）。

1. 默认绑定（独立函数调用）

当函数不带任何修饰符被直接调用时，触发默认绑定：

- 非严格模式：this 指向全局对象（浏览器中为 window，Node.js 中为 global）。
- 严格模式（'use strict'）：this 为 undefined。

2. 隐式绑定（作为对象的方法调用）

当函数被某个对象拥有并作为其方法调用时，this 指向直接调用它的那个对象。如果把对象的方法赋值给一个变量，或者作为回调函数传入定时器/事件监听器中，调用时丢失了上下文对象，会退化为默认绑定：

3. 显式绑定（call、apply、bind）

开发者通过内置方法强制指定函数执行时的 this 指向：

- fn.call(obj, arg1, arg2)：立即执行函数，参数逐个传入。
- fn.apply(obj, [arg1, arg2])：立即执行函数，参数以数组形式传入。
- const boundFn = fn.bind(obj, arg1)：不立即执行，而是返回一个永久绑定了 this 的新函数（硬绑定，后续无法再通过 call/apply 修改其 this）。

4. new 绑定（构造函数调用）

使用 new 关键字调用函数时，引擎会在底层创建一个全新的空对象，并将构造函数内部的 this 绑定到这个新创建的实例对象上。

## JavaScript中执行上下文和执行栈是什么？

执行上下文是代码被解析和执行时的抽象环境，而执行栈（Execution Stack，也叫调用栈 Call Stack）则是用来管理这些执行上下文的数据结构。

- 全局执行上下文（Global）：默认的基础环境，不在任何函数内的代码都在这里。浏览器中它关联 window 对象，整个程序只有一个。
- 函数执行上下文（Functional）：每次调用函数时都会为该函数创建一个全新的上下文。
- Eval 执行上下文：运行在 eval 函数内部的代码（极少使用）。

每当创建一个执行上下文，JavaScript 引擎都会按顺序执行两个阶段：

1. 创建阶段（Creation Phase）：代码尚未开始逐行执行。

- 创建词法环境 / 变量环境：扫描变量和函数声明。var 变量和函数声明会在这里发生变量提升（Hoisting），let 和 const 会被放入“暂时性死区”。
- 建立作用域链（Scope Chain）：确定当前环境能访问哪些外部变量。
- 确定 this 指向：根据函数的调用方式确定 this 的值。

2. 执行阶段（Execution Phase）：

执行栈就是引擎用来追踪多个函数调用的后进先出（LIFO）列表。

1. 程序启动：创建全局执行上下文，压入（Push）执行栈底部。
2. 调用 first()：创建 first 的执行上下文，压入栈顶。此时 first 在栈顶，开始执行。
3. 调用 second()：在 first 内部调用了 second，创建 second 的执行上下文，压入栈顶。first 暂停，开始执行 second。
4. second() 执行完毕：second 的上下文从栈顶弹出（Pop）并销毁。控制权交还给栈顶的 first。
5. first() 执行完毕：first 的上下文从栈顶弹出并销毁。控制权交还给全局上下文。
6. 程序结束：关闭页面或进程时，全局上下文弹出。

## typeof 与 instanceof 区别

typeof 用来检测基本数据类型，instanceof 用来检测引用数据类型

## 说说new操作符具体干了什么？

1. 创建一个全新的空对象：在内存中开辟空间，创建一个空对象。
2. 绑定原型链（链接 [[Prototype]]）：将这个新对象的内部原型（__proto__）指向构造函数的 prototype 属性（即 obj.__proto__ = Constructor.prototype）。
3. 绑定 this 并执行构造函数：将构造函数内部的 this 指向这个新创建的对象，并传入参数执行构造函数体内的代码，从而为新对象挂载实例属性。
4. 判断返回值并返回对象：如果构造函数显式返回了一个引用类型，则 new 表达式最终直接返回这个引用类型，之前创建的新对象会被丢弃，如果构造函数没有返回值，或者返回的是基本数据类型，则忽略该返回值，默认返回第一步创建的新对象。

## bind、call、apply 区别？

call，apply都是立即执行，只是接收参数的形式不同，call逐个接收多个参数，apply以数组的形式接收多个参数，bind不会立即执行，支持分批接收参数（绑定时创一部分，调用时创一部分），返回一个新函数，常用于事件回调，定时器或React组件中防止this丢失等。

## 说说你对事件循环的理解

事件循环（Event Loop）是 JavaScript 实现“单线程非阻塞异步执行”的核心调度机制。

1. 事件循环的核心组成

在浏览器环境中，异步任务被严格划分为两种不同优先级的队列：

- 微任务队列（Microtask Queue）：优先级最高，：Promise.then / catch / finally、async / await（await 后面的代码相当于在 .then 中执行）、MutationObserver、queueMicrotask。
- 宏任务队列（Macrotask Queue / Task Queue）：优先级较低，常见来源：整体 script 脚本代码、setTimeout、setInterval、DOM 事件回调（如 click）、I/O 操作、requestAnimationFrame（通常在渲染前触发）。

2. 浏览器事件循环的完整执行流程

每一次事件循环（称为一个 Tick）都严格遵循以下闭环顺序：

1. 执行同步代码：从宏任务队列中取出一个宏任务（初始时就是整个 `<script>` 标签的代码），压入执行栈中逐行执行。期间遇到的异步任务会交给浏览器对应线程处理，并在时机成熟时将回调分别放入微任务队列或宏任务队列。
2. 清空所有微任务：当前宏任务执行完毕、执行栈清空后，引擎会立即检查微任务队列。只要微任务队列不为空，就会按先进先出顺序连续执行，直到彻底清空（如果在执行微任务的过程中又产生了新的微任务，也会在当前轮次一并执行完）。
3. UI 渲染（按需执行）：浏览器判断是否需要更新页面视图（通常跟随屏幕刷新率，如 60Hz 约 16.6ms 一次），执行样式计算、布局和绘制。
4. 开启下一轮循环：从宏任务队列中取出队首的下一个宏任务，压入执行栈开始执行，重复上述步骤 1 -> 2 -> 3。

Node.js：将宏任务细分为 6 个固定阶段（Timers、Pending Callbacks、Idle/Prepare、Poll、Check、Close Callbacks）。此外，Node.js 还有一个专属的 process.nextTick()，它的优先级比普通微任务（Promise.then）还要高。

## 说说 JavaScript 中内存泄漏的几种情况？

1. 意外的全局变量：在非严格模式下，未用 let、const 或 var 声明的变量，或者普通函数中误指向 window 的 this，都会直接挂载到全局对象 window 上。全局对象的生命周期与整个页面一致，永远不会被自动回收。

2. 被遗忘的定时器（setInterval / setTimeout）：只要定时器没有被清除，它的回调函数以及回调内部引用的所有外部变量就会一直存活在内存中，即使关联的 DOM 节点已经被移除。在组件卸载或不再需要时，务必调用 clearInterval(timerId) 或 clearTimeout(timerId)。

3. 游离的 DOM 引用（Detached DOM）：当一个 DOM 元素已经从页面文档中移除（如调用了 el.remove()），但如果 JavaScript 变量或对象依然保存着对该 DOM 节点的引用，那么整个 DOM 节点（甚至连带它的整棵父/子 DOM 树）都无法被内存回收。移除 DOM 元素后，同步将 JS 中的引用置空（elements.button = null），或使用 WeakMap / WeakSet 来存储以 DOM 节点为键的元数据（弱引用不会阻止垃圾回收）。

4. 不当使用闭包（Closure）：闭包本身不是内存泄漏，但如果内部函数长期存活（例如被绑定为全局事件监听器或返回给外部长期保存），它就会锁住外层函数作用域中所有被引用的变量，导致这些变量无法释放。只保留闭包真正需要的精简数据，或者在不再使用时手动解除对闭包函数的引用。

5. 未销毁的事件监听器：给 DOM 元素或 window / document 绑定了事件监听器，但在单页应用（SPA）路由切换或组件销毁时忘记移除，会导致监听器及其引用的组件实例一直驻留内存。在销毁阶段成对调用 removeEventListener('resize', handler)（注意传入的必须是同一个函数引用）。对于只需触发一次的事件，直接传入配置项 { once: true }；或使用 AbortController 统一批量取消多个事件监听。

6. 无限增长的缓存（Map / Set / 数组）：在前端做数据缓存或事件订阅发布（EventBus）时，如果只往全局 Map 或数组中不断 push 数据，却没有设置容量上限或淘汰机制，缓存就会随着用户操作无限膨胀。如果缓存的键是对象或 DOM 节点，优先使用 WeakMap 或 WeakSet（当外部对象销毁时，缓存项会自动被垃圾回收）。如果是普通字符串键，手动实现 LRU（最近最少使用）缓存淘汰策略，限制最大缓存条数。

排查内存泄漏的实用工具

当怀疑页面存在内存泄漏时，可以直接打开 Chrome DevTools 的 Memory（内存） 面板：

1. Heap Snapshot（堆快照）：在执行某项操作前后分别拍摄堆快照，通过对比（Comparison）视图，筛选查找标有 Detached（游离 DOM）或数量持续增长的对象。
2. Performance Monitor（性能监视器）：实时观察 JS Heap Size（JS 堆内存大小）曲线——如果多次手动点击垃圾回收图标（小垃圾桶）后，内存基准线依然呈阶梯式上升，就说明存在内存泄漏。

## 说说你对函数式编程的理解？优缺点？

- JS中函数是一等公民（First-Class Functions）：函数与数字、字符串一样，可以赋值给变量、作为参数传递给其他函数，也可以作为返回值从函数中输出。
- 函数式编程的基石，必须同时满足两个条件：

1. 相同输入永远得到相同输出（不依赖外部可变变量或随机数/时间）。
2. 无副作用（Side Effects）（不修改外部变量、不修改传入的引用参数、不发起网络请求或操作 DOM）。

- 数据不可变性（Immutability）：数据一旦创建就不能被直接修改。如果需要更新数据（如向数组添加一项），必须返回一个包含新值的副本（如 [...arr, newItem]），原数据保持原样。
- 高阶函数（Higher-Order Functions）：接收函数作为参数，或返回一个新函数的函数（例如 Array.prototype.map、防抖节流包装函数、以及前面聊到的 bind）。
- 柯里化：将接收多个参数的函数拆解为一系列只接收单个参数的函数（fn(a, b, c) \(\rightarrow \) fn(a)(b)(c)），便于参数复用。
- 函数组合：像搭积木或流水线一样，将多个小函数串联成一个大函数（compose(f, g)(x) 相当于 f(g(x))）。

优点（优势）：

- 代码可读性与可维护性高：声明式代码直接表达业务意图，链式调用像阅读自然语言一样清晰。
- 极易测试与调试：纯函数只依赖输入参数，不依赖外部环境，写单元测试时不需要复杂的 Mock 环境；且因没有共享状态被意外篡改，排查 Bug 非常容易。
- 天然并发安全：由于数据不可变，多个线程或异步任务同时读取同一份数据时不会发生竞态条件（Race Condition）或数据覆盖冲突。
- 高度模块化与复用性：通过柯里化和函数组合，细粒度的工具函数可以像乐高积木一样灵活拼装在不同业务中。

缺点（局限）：

- 频繁创建新对象/新数组（不可变性）会增加内存分配和垃圾回收（GC）的压力。
- 大量使用递归（如前面聊到的尾递归）和多层高阶函数闭包嵌套，在 JS 引擎未开启尾调用优化的情况下容易造成额外的执行栈开销。

## Javascript中如何实现函数缓存？函数缓存有哪些应用场景？

函数缓存是一种利用闭包和哈希表将函数每次的“输入参数”与“计算结果”映射存储起来的优化技术，本质上是用内存空间换取 CPU 计算时间。如果函数本身计算极快，引入序列化参数和查找 Map 的开销反而比直接计算更慢，典型应用场景：

- 递归算法与动态规划优化（避免重复子问题计算）
- 昂贵的数据处理与复杂计算，如前端对上万条表格数据进行多条件过滤排序、大数据图表坐标转换、复杂的正则匹配解析、或者客户端加密哈希计算。只要筛选条件不变，切换 Tab 回来时直接读取缓存。
- 前端框架中的派生状态计算（如 React useMemo / Vue computed），在现代前端框架中，组件每次重新渲染都会重新执行内部函数。React 的 useMemo 和 React.memo、Redux 生态的 reselect 库，底层本质上都是单次容量（maxSize = 1）的函数缓存——只有当依赖项（参数）发生变化时才重新计算，否则直接复用上次渲染的引用。
- 幂等性异步接口请求缓存（防重复请求）

## 说说 Javascript 数字精度丢失的问题，如何解决？

JS 只有一种数字类型（Number），它是标准的 64 位双精度浮点数（Double Precision Floating-Point），导致部分十进制小数在转为二进制时出现无限循环，以及超大整数超出安全表示范围。

- 电商购物车、财务结算、利率计算：使用decimal.js 或 bignumber.js
- 后端返回 18~19 位长整型 ID（如雪花 ID）：后端转 String 下发，或前端使用 BigInt / json-bigint
- 判断两个浮点数计算结果是否相等：使用Math.abs(a - b) < Number.EPSILON
- 简单优惠券金额展示：后端直接存储整数“分”，前端展示时除以 100

## 什么是防抖和节流？有什么区别？如何实现？

防抖（Debounce）与节流（Throttle）都是用来限制高频事件触发频率的性能优化技术，核心区别在于：防抖是“连续触发只执行最后一次（重新计时）”，而节流是“连续触发时按固定时间间隔均匀执行（稀释频率）”。

应用场景：

- 防抖：搜索框实时联想输入、表单输入格式校验、窗口 resize 结束后的布局重算、按钮防连点提交。
- 节流：页面滚动加载（scroll）、鼠标移动（mousemove）拖拽位置计算、射击游戏按键发射频率控制。

## 如何判断一个元素是否在可视区域中？

- IntersectionObserver：浏览器原生异步监听元素与视口的交叉状态，性能极高（不阻塞主线程，无重排），适合图片懒加载、无限滚动、广告曝光埋点
- getBoundingClientRect()：获取元素边界矩形相对于视口左上角的坐标，性能一般（需配合 scroll 事件及节流，易触发重排），适合需要精确计算像素距离、兼容老旧浏览器
- offsetTop + scrollTop：累加计算元素距页面顶部总高度，与滚动距离对比，性能较差（需循环向上遍历 offsetParent，易触发重排），早期方案，现代开发已基本被前两种替代

## 大文件上传如何做断点续传？

大文件断点续传的核心原理是：在前端将大文件按固定大小切割成多个小切片（Chunk），并为文件生成唯一的 内容 Hash 标识；上传时通过后端接口查询已成功上传的切片列表，跳过已传部分，仅并发上传剩余缺失的切片，最后由服务端按序合并成完整文件。

1. 文件切片（File Slicing）：利用浏览器原生的 File.prototype.slice 方法（继承自 Blob），将几 GB 的大文件按固定大小（例如 2MB 或 5MB）切割成若干个二进制切片数组。slice 操作在底层只是创建文件指针引用，不会把整个文件一次性读入内存，速度极快。
2. 计算文件唯一标识（File Hash）：不能使用文件名作为唯一标识（不同用户可能上传同名但内容不同的文件），必须根据文件内容计算 MD5 / SHA-256（常用 spark-md5 库），大文件全量计算 Hash 会阻塞主线程导致页面卡死，实际开发中通常采用 Web Worker 后台线程计算 + 抽样 Hash（首尾切片全量 + 中间切片抽样），可将几 GB 文件的 Hash 计算时间从数十秒压缩至 1 秒以内。
3. 上传前握手校验（秒传与断点查询）：前端携带 fileHash 和 fileName 请求后端的 verify（校验）接口，后端根据记录返回三种状态之一：

- 已完整存在（秒传）：服务器磁盘/OSS 中已有该 Hash 对应的完整文件，直接返回成功，无需上传任何切片。
- 从未上传过：返回空列表 []，前端从第 0 个切片开始全量上传。
- 部分已上传（断点续传）：返回已成功落盘的切片索引列表（如 [0, 1, 2, 5]），前端过滤掉这些切片，仅上传缺失的切片（如 3, 4, 6...）。

4. 并发控制与失败重试（Concurrency & Retry）：剩余切片通过 FormData 封装（携带切片二进制数据、chunkHash、index、fileHash）并发发送，浏览器对同一域名有最大并发连接数限制（通常为 6 个），一次性发出几百个请求会导致请求排队超时或内存飙升，需编写并发请求池（每次最多同时发 3~5 个请求），并为单个切片配置自动重试机制（如失败重试 3 次）。
5. 暂停与恢复控制（Pause & Resume）：暂停：利用 AbortController（配合 fetch 或 axios）直接中止当前正在传输中的 HTTP 请求，并停止调度队列中的后续切片，再次触发上传流程（重新请求 verify 接口获取最新已传切片列表，继续发送剩余切片即可）。
6. 服务端切片合并（Merge）：当所有缺失切片均上传成功后，前端通知后端调用 merge 接口，后端根据 fileHash 找到临时目录中的所有切片，按切片序号 index 排序后，利用 Node.js 的 Stream（可读流/可写流 pipe） 逐个追加写入目标文件，合并完成后校验最终文件 Hash 并清理临时切片目录。

生产环境进阶优化细节

- 动态调整切片大小（慢启动策略）：参考 TCP 拥塞控制，先发一个 2MB 试探切片测量当前网速，网速快则自动调大至 10MB 减少 HTTP 请求次数；弱网环境则调小至 1MB 降低单次重传成本。
- 定期清理碎片垃圾：用户可能上传到一半就彻底放弃了，后端需要配置定时任务（Cron Job），自动清理超过 24 小时或 7 天未完成合并的临时切片目录，防止撑爆服务器磁盘。
- 直接对接云存储 OSS 分片上传：在大型商业项目中，通常不让大文件流量经过自己的业务后端服务器，而是由后端签发临时凭证（STS Token），前端直接调用 阿里云 OSS / AWS S3 / 腾讯云 COS 原生提供的 multipartUpload SDK 完成分片断点续传。

## 什么是单点登录？如何实现？

单点登录（Single Sign-On，简称 SSO）是一种身份认证机制，允许用户在多个相互信任的独立应用系统中，只需登录一次，即可无需重复输入账号密码直接访问所有关联系统。

一、 核心实现方案对比

1. 同父域 Cookie 共享：适用于同一主域名下的不同子域名（如 ://a.com 与 ://a.com），使用浏览器 Cookie（设置 Domain=.a.com），传统 Session + Redis 共享存储 / JWT
2. 独立认证中心（重定向 + 令牌）：适用于完全不同的独立域名（如 taobao.com 与 tmall.com），使用全局认证中心 Session + 一次性票据（Ticket/Code）+ 局部 Token，如OAuth 2.0
3. 前端跨域通信同步Token：适用于完全不同的独立域名，localStorage + postMessage / 隐藏 iframe，自定义统一登录中心前端页 + JWT

二、生产环境关键安全与架构细节

- 单点登出（Single Log-Out, SLO）：用户在一个系统点击“退出登录”时，系统不仅要清除自身的局部 Token，还必须通知认证中心销毁全局会话；认证中心再通过后端回调接口或前端隐藏 iframe 广播通知所有已登录的子系统同步清理各自的局部登录态。
- 防范重放与劫持风险：URL 中传递的一次性票据（code / ticket）必须设置极短有效期（如 30 秒~1 分钟）且验证一次后立即作废，防止 URL 泄露在浏览器历史记录或代理日志中被他人冒用。
- 现代主流协议选型：新项目建议直接采用基于 OAuth 2.0 扩展的 OIDC（OpenID Connect） 标准协议，开源或商业成熟方案可选用 Keycloak、Auth0、Casdoor 或 Okta，避免从零手写安全认证协议。

## 你是怎么理解ES6中 Promise的？使用场景？

ES6 中的 Promise 是一种用于管理异步操作的标准对象，它代表了一个异步任务在未来某个时刻才会产生的最终结果（成功的值或失败的原因）。Promise 通过状态机机制和链式调用，把异步操作的控制权重新收归调用者手中。常见的使用场景有：

1. 串联存在前后依赖的异步请求（消除回调地狱）：当第二个接口的参数依赖第一个接口的返回值时（例如：登录获取 Token -> 用 Token 获取用户信息 -> 根据用户角色拉取菜单），通过链式调用（或配合 async/await）清晰编排：
2. 多任务并发请求与批量聚合（Promise.all / Promise.allSettled）：在页面初始化时，如果多个数据源互不依赖，使用并发组合器同时发出请求，将总耗时从“所有请求耗时之和”压缩为“最慢那个请求的耗时”：

- Promise.all([p1, p2, p3])（全成功才算成功）：适合强依赖场景（如必须同时拿到商品详情、库存状态和优惠券才能渲染下单页），只要有一个失败就会立刻整体失败（Fail-fast）。
- Promise.allSettled([p1, p2, p3])（无论成败全部等完）：适合仪表盘多模块独立加载、批量上传多张图片等容错场景，能拿到每个任务的独立成功值或失败原因，互不拖累。

3. 请求超时控制与多源竞速（Promise.race / Promise.any）

- 接口超时熔断（Promise.race）：将真实网络请求与一个设定好延迟拒绝的定时器 Promise 放在一起竞速，哪个先完成就采用哪个结果；
- 多 CDN 节点择优（Promise.any）：同时向多个备用节点请求同一资源，只要任意一个率先成功就立即返回，只有全部节点都失败时才报错。

4. 将传统回调式 API 改造为现代异步接口（Promisify 封装）：在维护老旧 SDK 或调用基于事件/回调的原生 API（如 setTimeout、旧版微信 JS-SDK、图片加载 img.onload、Node.js 早期回调函数）时，用 new Promise 包装一层，使其能够直接配合 await 使用：

5. 请求去重与并发缓存（Singleton Promise 缓存）：当页面上多个独立组件在同一毫秒内同时请求同一个配置接口（如 /api/system-config）时，可以直接将正在 Pending 中的 Promise 实例本身缓存起来返回给所有调用方——网络请求只会真正发出一次，等结果回来后所有组件共享同一份返回值。

## 怎么理解ES6中 Generator的？使用场景？

ES6 中的 Generator（生成器）是一种可以被“暂停执行”并在之后任意时刻“恢复执行”的特殊函数（通过 function* 声明并配合 yield 关键字使用）。常见的使用场景有：

1. 异步编程的同步化表达（async/await 的底层前身与复杂异步流控制）：虽然现代日常异步请求首选 async/await（async/await 本质上就是 Generator + Promise + 自动执行器 的语法糖），但在需要精细控制异步任务取消、竞速、重试或并发编排的复杂场景中（如 React 生态著名的 redux-saga），Generator 依然不可替代
2. 惰性求值与无限数据序列（Lazy Evaluation）：由于 Generator 是“按需计算”的（只有调用 .next() 才会算下一个值），它可以用极低的内存开销表示无限长度的数据流（如斐波那契数列、自增 ID 生成器、无限分页数据流），完全不会造成死循环或内存溢出
3. 快速为自定义数据结构部署可迭代接口（[Symbol.iterator]）：任何对象只要部署了 [Symbol.iterator] 方法，就能被 for...of、... 扩展运算符和 Array.from() 消费。手动编写状态机迭代器非常繁琐，而用 Generator 只需几行代码即可实现
4. 实现轻量级状态机（State Machine）：对于具有明确状态流转规则的业务组件（如红绿灯切换、表单多步骤向导、游戏角色状态切换），使用 Generator 可以把状态转换逻辑收敛在单一循环中，无需维护外部散落的 currentState 标志位
5. 在现代 ES2018+ 中，结合了 async/await 与 Generator 的异步生成器（async function*），配合 for await...of 循环，已成为处理流式接口响应（如大模型 SSE 打字机流式输出、分块读取大文件、分页接口自动遍历拉取）的标准利器。

## 你是怎么理解ES6中Proxy的？使用场景?

ES6 中的 Proxy（代理）是 JavaScript 元编程（Metaprogramming）的核心特性，它允许你为目标对象创建一个“拦截代理层”，在外界访问、修改、删除对象属性或调用函数时，提前拦截并自定义这些底层基本操作的默认行为。常见的使用场景有：

1. 现代前端框架的响应式系统：Vue 3 的 reactive() 底层完全基于 Proxy 构建：当组件渲染读取属性时触发 get 收集依赖（Track），当状态被修改时触发 set 通知对应组件精准重渲染（Trigger）；
2. 数据校验、类型约束与私有属性保护：在赋值前自动校验数据类型或取值范围，并拦截外部对内部私有属性（如 _ 开头字段）的读写与枚举；
3. 不可变数据（Immutability）的实现：像 Immer.js 这样的现代不可变状态库，正是利用 Proxy 包裹原始状态树，允许开发者以“看似直接修改对象（draft.user.name = 'Bob'）”的直观写法编写代码，而 Proxy 在后台静默拦截所有修改并生成结构共享（Structural Sharing）的新对象副本，原对象丝毫不受影响。
4. 负索引数组与安全默认值兜底（增强原生结构）：通过拦截 get 操作，实现类似 Python 的数组负索引访问（arr[-1] 获取最后一个元素），或者为不存在的属性自动提供默认值，防止深层取值报 Cannot read properties of undefined：
5. 缓存代理、API 链式动态构建与性能监控

- 函数调用拦截（apply）：代理函数对象，实现参数自动缓存（Memoization）、权限校验或自动记录接口请求日志。
- 优雅的链式 API 客户端：利用 get 拦截器动态捕获任意属性路径，无需提前手写几十个接口方法即可实现 api.users.profile.get({ id: 1 }) 自动映射到 GET /users/profile?id=1。

## 你是怎么理解ES6中Module的？使用场景？

1. 静态化结构（Static Structure）：

- import 和 export 必须位于模块顶层，且路径只能是静态字符串字面量（不能写在 if 语句里动态拼接路径）。
- 直接红利：让打包工具（Vite、Rollup、Webpack）能在构建阶段精准分析模块依赖图，自动剔除未被使用的死代码（Tree-shaking），大幅减小最终产物体积。

2. 实时动态绑定（Live Binding，只读引用）：

- CommonJS 导出的是值的拷贝（导出后内部变量再变，外部也拿不到最新值）；而 ESM 导出的是内存地址的只读实时引用。如果模块内部修改了导出的变量值，外部导入的地方会同步看到最新值（但外部不能直接重新赋值修改它）。

3. 自带独立作用域与默认严格模式：

- 每个模块文件都是一个完全独立的词法作用域，顶层声明的 var / let / const 绝不会挂载到全局 window 对象上。
- 模块内部自动强制开启 "use strict"（严格模式），顶层的 this 指向 undefined 而非 window。

4. 单例执行与异步加载：

- 同一个模块无论被多少个文件 import 多少次，只会在首次加载时执行一次，后续导入直接复用缓存的模块实例；在浏览器中通过 <script type="module"> 引入时，默认等同于 defer（异步下载、不阻塞 HTML 解析、按序执行）。

常见的使用场景有：

1. 大型前端与 Node.js 项目的架构分层与高内聚拆分（基础场景）

将复杂应用拆分为职责单一的小文件，通过显式的 import / export 契约管理依赖：
- api/ 目录封装网络请求模块
- utils/ 目录封装纯工具函数（日期格式化、金额计算）
- components/ 目录封装独立 UI 组件，彻底告别全局变量污染和脚本引入顺序地狱。

2. 路由懒加载与按需动态加载（Dynamic import()）

虽然静态 import 只能写在顶层，但 ES2020 引入了原生的函数式动态导入 import(specifier)（返回一个 Promise），完美解决首屏加载体积过大的问题：

- 前端路由代码分割（Code Splitting）：用户只有点击进入“个人中心”或“报表页面”时，才动态下载该页面的 JS 模块。
- 按需加载重型第三方库：例如用户点击“导出 Excel”按钮时，才通过 const XLSX = await import('xlsx') 临时加载体积庞大的解析库。

3. 编写通用工具库与实现极致 Tree-shaking（开源 SDK 场景）

在开发内部组件库或通用工具库（如 lodash-es、date-fns）时，坚持使用命名导出（export function ...）而非把所有方法挂载到一个默认导出的大对象上：

- 业务方只需 import { formatDate } from 'my-utils'，构建工具就能在打包时把库里其余几十个未用到的函数彻底剔除。

4. 原生浏览器无构建工具开发（No-Build / Micro-Apps）

现代主流浏览器已原生支持 `<script type="module">` 配合 Import Maps（导入映射）。在开发小型内部工具、原型验证或微前端子应用时，无需配置复杂的 Webpack/Babel，直接用原生 ESM 即可模块化引入第三方 CDN 包（如 esm.sh）并运行。

5. 单例模式（Singleton）与全局状态共享

利用 ESM“无论被导入多少次，模块顶层代码只执行一次”的特性，天然实现轻量级单例：

- 例如在 config.js 或 eventBus.js 中实例化一个配置对象或事件总线并 export default instance，全项目所有导入该文件的模块都会自动共享同一个实例引用，无需手写复杂的单例判断逻辑。

## 你怎么看 AMD vs. CommonJS？

AMD 和 CommonJS 都是 JavaScript 早期在没有官方模块化标准（ES6 Modules）时期，由社区分别针对“浏览器端”和“服务端（Node.js）”提出的模块化规范。

CommonJS (CJS)：服务端（Node.js），后经 Browserify/Webpack 打包引入前端，同步加载（Synchronous），服务端模块全在本地硬盘上，读取速度极快（微秒级），同步阻塞几乎无感。按需执行（Lazy）：代码执行到 require() 那一行时，才真正加载并执行目标模块。值的拷贝（浅拷贝）：一旦输出，模块内部后续变化不会影响外部已获取的原始值。
AMD (Asynchronous Module Definition)：浏览器端（代表实现库：RequireJS），异步加载（Asynchronous），浏览器需通过网络下载 JS 文件，若同步加载会导致页面白屏卡死，必须异步非阻塞。前置执行（Eager）：在回调执行前，提前把依赖数组里的所有模块全部下载并执行完毕。导出对象引用或工厂函数返回值（同样是运行时动态计算）。

## 什么是闭包 (closure)，如何使用它，为什么要使用它？

闭包（Closure）是指一个函数能够记住并访问其词法作用域（Lexical Scope），即使该函数在其词法作用域之外被调用执行。构成闭包通常需要满足三个基本条件：函数嵌套、内部函数引用外部函数变量、内部函数被暴露到外部。

1. 实现私有变量与数据封装（模拟私有属性）：JavaScript 早期没有原生 private 关键字，开发者通过闭包将敏感状态锁在函数作用域内部，只向外暴露受控的操作接口，防止外部代码随意篡改。

2. 函数工厂与柯里化（预设参数 / 配置复用）：通过闭包“记住”初次传入的配置参数，生成具有特定行为的专用函数，减少重复传参：

3. 缓存计算结果（Memoization 记忆化优化）：利用闭包在内存中维护一个私有缓存字典（如 Map 或 {}），遇到相同入参时直接返回缓存结果，避免重复执行高耗时计算：

4. 现代前端框架与异步回调的状态保持

- React Hooks（如 useState、useEffect）：底层完全依赖闭包机制，让每次组件重新渲染时的钩子函数都能准确读取到对应索引位置的历史状态（同时这也是 React 中出现“闭包陷阱 / Stale Closure”的根源）。
- 事件监听与异步回调：在循环或异步请求发起时，通过闭包保存发起瞬间的上下文参数（如当前循环索引或订单 ID）。

## 你是如何组织自己的代码？是使用模块模式，还是使用经典继承的方法？

优先采用基于 ES Modules（模块模式）配合“组合优于继承（Composition over Inheritance）”及函数式编程的架构来组织代码，仅在极少数明确需要构建层级化领域模型或自定义异常时，才会适度使用经典 class 继承。

- ES Modules 模块模式(import / export)，每个文件拥有独立词法作用域，显式声明输入输出依赖，原生支持静态分析和构建期摇树优化（Tree-shaking）。
- 函数式组合 / Hooks(Composition & Pure Functions)，业务逻辑首选，将复杂逻辑拆分为无副作用的纯函数或自定义 Hook，像搭积木一样按需组装，避免共享可变状态。适用场景有UI 组件复用（React Hooks / Vue Composables）、数据处理管道、通用工具库。
- 经典继承 (class ... extends)，通过原型链实现属性与方法复用，封装内部状态与行为，支持多态（Polymorphism）。适用场景有自定义错误类 / Web 端通用播放器 / 富文本插件 / WebSocket 实时通信客户端 / 多渠道支付 / 第三方登录 / 仓储适配器。
- 传统闭包模块模式 (IIFE)，在 ES6 之前利用 (function() { ... })() 模拟私有变量和公有接口，防止全局污染。维护无法引入现代打包工具的极老旧浏览器脚本，或编写独立注入页面的轻量级第三方埋点片段。

## 请解释变量声明提升 (hoisting)

变量声明提升（Hoisting）是 JavaScript 引擎在正式逐行执行代码前的编译阶段，将当前作用域内的变量和函数声明提前登记到内存中的机制。

1. function fn() {}（函数声明）：完全提升（声明 + 函数体一起提升）

## js 代码压缩 minify 的原理是什么

1. 解析源码为 AST（Parsing）：先通过词法分析（Tokenizer）和语法分析（Parser）将 JS 源码转换成 AST（抽象语法树），在这一步，所有的空白符（空格、换行、制表符）和注释都会在词法分析阶段被直接丢弃。

2. 代码转换与逻辑优化（Transformation / Compression）：在遍历 AST 的过程中，压缩器会应用大量编译原理中的静态优化规则，进一步缩减代码体积并提升执行效率：

- 死代码消除（Dead Code Elimination, DCE）：删除永远不会执行到的代码分支或未被引用的变量。javascript
- 常量折叠与预计算（Constant Folding）：在编译阶段直接算出静态表达式的结果。javascript
- 语法精简与等价替换：将冗长的写法替换为等效的极简表达式。

3. 变量名混淆与作用域分析（Mangling）：这是体积缩减最显著的一步。压缩器会构建完整的作用域树（Scope Tree），分析每个变量的生命周期和引用关系：

- 缩短标识符：将局部变量名、函数参数名、私有方法名重命名为单字母，单字母用完后再使用双字母。
- 跨作用域名字复用：不同函数内部互不冲突的局部变量，会复用相同的单字母（例如函数 A 里的参数叫 e，函数 B 里的局部变量也叫 e），这不仅减小体积，还能大幅提升后续 Gzip / Brotli 网络压缩的重复率。

4. 代码生成与 SourceMap 映射（Code Generation）：最后，生成器（Generator）遍历优化后的 AST，将其重新序列化为紧凑的字符串：

- 剔除多余分号与括号：仅保留语法解析必须的分隔符（如语句末尾最后一个花括号前的分号可省略）。
- 生成 SourceMap（.map 文件）：在输出每个混淆后的节点时，同步记录其对应的原始源码文件名、行号和列号（采用 VLQ 编码压缩映射表），供开发调试和线上错误监控还原堆栈（即前面讨论的堆栈还原机制）。

## 如何在 url 中传递数组

1. 重复键名（最常用、最标准），大多数现代后端框架（如 Spring MVC、Node.js、Python/Flask/Django）默认支持，会将相同 Key 的值自动组合成一个数组，部分老旧框架或特定语言可能只接收最后一个值（如部分 PHP 配置）或只接收第一个值（如部分 Java 配置）。

2. 逗号分隔（最简短），URL 结构最干净，不会产生冗长的键名，后端无法自动识别为数组，必须先用 split(',') 手动切割成数组；如果数组元素本身包含逗号，则需要额外进行 URL 编码转义。

3. 带下标（[] 或索引），在 PHP、Express (Node.js) 等生态中非常流行，能清晰表达层级或数组结构，中括号 [] 属于 URL 特殊字符，在某些高版本 Web 容器（如 Tomcat）中直接发送可能会报 400 Bad Request 错误，前端必须使用 encodeURIComponent() 进行编码。

4. JSON 字符串化（适合复杂结构/长数组），适合传递结构复杂的对象数组或超长数据，URL 会变得极其冗长且难以阅读，且受浏览器对 URL 最大长度（通常几 KB）的限制。

## 如何实现 compose 函数，进行函数合成

compose 函数通过将多个函数串联，把前一个函数的返回值作为后一个函数的参数，从而实现函数的右向左组合执行（即 compose(f, g)(x) 等价于 f(g(x))），使用 compose 的本质价值在于解耦与复用：每个小函数只负责单一职责（纯函数），通过灵活排列组合就能拼装出复杂的业务逻辑，代码也更容易做单元测试。有以下场景会使用到：

1. 数据清洗与转换管道（Data Pipelines），当数据需要经过一系列连续的格式化、过滤或计算时，使用 compose（或从左到右的 pipe）可以避免写大量中间变量或深层嵌套代码。

2. Web 框架的中间件机制（如 Redux、Koa），这是 compose 在前端工程中最著名的落地场景，用于按顺序增强核心逻辑。

- Redux (applyMiddleware)：Redux 内部自带 compose 函数，将日志记录（Logger）、异步请求（Thunk/Saga）等多个中间件层层包裹在 dispatch 方法外围，实现 Action 派发前的拦截与处理。
- Koa (koa-compose)：虽然实现上增加了 next 指针（形成洋葱模型），但其本质依然是通过函数合成将多个异步中间件串联成一个大的执行函数。

3. React 高阶组件（HOC）组合

在 React 开发中，当一个组件需要同时接入路由、状态管理、权限校验等多个高阶组件时，嵌套调用会导致“地狱括号”。

4. 构建工具的 Loader / Plugin 链，Webpack 内部正是采用类似 compose 从右向左的执行顺序，将前一个 Loader 编译出的字符串交给下一个 Loader 继续处理。

## 有没有遇到 js 捕捉不到异常堆栈信息的情况

1. 跨域脚本触发 Script error.（最常见，完全无堆栈）

- 现象：全局 window.onerror 捕获到的错误信息只有孤零零的 "Script error."，行号、列号为 0，error 对象为 null，完全没有堆栈。
- 原因：当网页加载了来自不同域名（如 CDN）的 JS 文件，且该脚本抛出了未捕获异常时，浏览器出于同源安全策略（防止恶意网站窥探第三方脚本内部信息），会刻意屏蔽所有错误细节。
- 解决方案（缺一不可）：前端标签加属性：在 `<script>` 标签上添加 crossorigin="anonymous"，CDN 服务端加响应头：为该 JS 静态资源配置 Access-Control-Allow-Origin: *（或指定允许的业务域名）。

2. 异步任务导致调用堆栈断裂（Stack Trace Truncation）

- 现象：在 setTimeout、addEventListener 或旧式回调函数内部报错时，error.stack 只能看到异步回调内部的几行代码，看不到最初是谁发起了这个异步任务。
- 原因：JS 是基于事件循环（Event Loop）运行的。当同步代码执行完毕、函数调用栈清空后，异步回调才被推入一个新的空调用栈中执行，原本的调用上下文已经销毁。
- 解决方案：尽量使用原生的 async / await 替代回调嵌套（现代 V8 引擎对 async/await 实现了“零开销异步堆栈追踪”，能自动保留跨越 await 的完整调用链），在复杂业务中，手动在触发异步前保留上下文信息（如记录 TraceID 或自定义错误包装 new Error('调用来源', { cause: originalError })）。

3. 生产环境代码压缩混淆（堆栈变成天书）

- 现象：虽然捕获到了 error.stack，但里面全是 at a (app.9f8a2.js:1:45210)，根本无法定位到源码具体哪一行。
- 原因：线上代码经过 Vite / Webpack 打包压缩，变量名被替换为单字母，所有代码被压成一行。
- 解决方案：构建时生成 SourceMap（.map 文件），但切记不要随静态资源直接部署到公网（防止源码泄露），在 CI/CD 构建阶段将 .map 文件上传至前端监控平台（如 Sentry、Arms），由监控平台在服务端自动还原出真实的源码行号与堆栈。

4. 未处理的 Promise 拒绝（window.onerror 抓不到）

- 现象：Promise.reject() 或 async 函数内部报错且没有写 .catch() 时，window.onerror 和 try...catch 完全不会触发。
- 原因：Promise 内部的异常会被 Promise 机制吞掉并转化为 rejected 状态，不会直接冒泡到传统的 window.onerror。
- 解决方案：必须额外监听全局事件：window.addEventListener('unhandledrejection', (event) => { ... })，通过 event.reason 获取错误对象和堆栈。

5. 特殊抛出方式导致丢失 stack 属性

- 现象：捕获到了错误，但打印 err.stack 为 undefined。
- 原因：代码中有人写了 throw "网络错误" 或 Promise.reject({ code: 500 })——抛出的不是 Error 实例，而是一个普通字符串或纯对象。只有通过 new Error() 实例化时，JS 引擎才会生成并挂载 .stack 调用栈快照。
- 解决方案：团队规范强制要求（可通过 ESLint 规则 no-throw-literal 约束）：所有 throw 和 Promise.reject 必须传入 new Error(...) 实例。

6. React / Vue 框架内部吞掉错误 & 浏览器插件干扰：需要通过 ErrorBoundary 的 componentDidCatch(error, info) 或 Vue 的 app.config.errorHandler 单独收集。

## 有没有用过 Promise.allSettled() ，它是干什么的

Promise.allSettled() 用于并行执行多个 Promise，并等待所有任务都“尘埃落定”（无论成功 fulfilled 还是失败 rejected）后，统一返回每个任务的最终状态和结果数组。
与 Promise.all() 遇到任何一个失败就立即中断（“全有或全无”）不同，Promise.allSettled() 永远不会因为某个子任务失败而进入 .catch()，非常适合处理互不依赖、允许部分失败的批量异步操作。

## 使用 js 实现一个 lru cache

在 JavaScript 中，实现时间复杂度为 O(1) 的 LRU（Least Recently Used，最近最少使用）缓存，最简洁且高效的方式是直接利用 ES6 Map 能够严格记住键值对插入顺序的特性。

```javascript
class LRUCache {
  constructor(capacity) {
    if (capacity <= 0) {
      throw new Error('Capacity must be greater than 0');
    }
    this.capacity = capacity;
    this.cache = new Map();
  }

  /**
   * 获取缓存：如果存在，将其刷新为“最新使用”（先删后插）
   */
  get(key) {
    if (!this.cache.has(key)) {
      return -1; // 或返回 undefined，视业务约定而定
    }

    const value = this.cache.get(key);
    // 刷新位置：删除旧位置，重新插入到 Map 尾部
    this.cache.delete(key);
    this.cache.set(key, value);

    return value;
  }

  /**
   * 写入缓存：如果已存在则更新并刷新位置；如果超出容量则淘汰头部最久未使用的项
   */
  put(key, value) {
    // 1. 如果 key 已存在，先删除旧记录（确保后续 set 时能排到最新位置）
    if (this.cache.has(key)) {
      this.cache.delete(key);
    }

    // 2. 写入最新位置
    this.cache.set(key, value);

    // 3. 若超出最大容量，淘汰 Map 中第一个（最久未使用）的键
    if (this.cache.size > this.capacity) {
      // this.cache.keys().next().value 可以 O(1) 获取 Map 的第一个键
      const oldestKey = this.cache.keys().next().value;
      this.cache.delete(oldestKey);
    }
  }
}
`

## 简述 node/v8 中的垃圾回收机制

1. V8 将堆内存主要分为两个核心区域：

- 新生代（New Space）：存放生存时间短、体积小的对象。空间较小（通常为 1MB ~ 32MB），垃圾回收非常频繁。
- 老生代（Old Space）：存放经过多次回收依然存活的对象，或体积较大的对象。空间大，回收频率低，但单次耗时相对较长。

2. 核心回收算法

- 新生代回收：将新生代平分为两个等大的半空间，From 空间（使用中）和 To 空间（空闲），新对象统一分配在 From 空间，触发回收时，检查 From 空间中的存活对象，将其复制到 To 空间并紧密排列（消除内存碎片），清空整个 From 空间，随后将 From 和 To 的角色互换。
经历过一次（或两次）回收后依然存活，或者复制时To 空间的内存占用已超过 25%），会被移动到老生代。

- 老生代回收：标记-清除（Mark-Sweep）与 标记-整理（Mark-Compact）

  - 标记-清除（Mark-Sweep）：从根对象（如 global、当前执行栈变量）出发遍历引用链，标记所有可达的存活对象，然后直接清除未被标记的垃圾对象，缺点是清除后会产生大量不连续的内存碎片，导致后续无法分配大对象。
  - 标记-整理（Mark-Compact）：当内存碎片严重、无法满足大对象分配时触发。在标记完成后，将所有存活对象向内存一端移动并紧密排列，最后清理掉边界以外的所有内存。

3. 性能优化机制

因为 JavaScript 是单线程运行的，传统 GC 执行时会阻塞主线程（即 Stop-The-World / 全停顿），导致页面卡顿或 Node 接口响应延迟。V8 引入了多项机制大幅减少主线程停顿时间：

- 增量标记（Incremental Marking）：将耗时的老生代标记过程拆分成许多小任务，穿插在 JS 主线程代码执行的间隙中分步完成。
- 并行回收（Parallel）：在执行全停顿时，开启多个辅助线程（Worker Threads）同时分担清理工作。
- 并发标记与清理（Concurrent）：辅助线程在后台与 JS 主线程完全同时运行完成对象标记和内存释放，几乎不占用主线程时间。

## fetch 中 credentials 指什么意思，可以取什么值

1. 'same-origin'（默认值）

- 含义： 同源请求时携带凭证，跨域请求时不携带。
- 表现： 如果你请求的是自己网站同域名下的接口（如 example.com 网页请求 ://example.com），浏览器会自动带上 Cookie。但如果你请求的是第三方跨域接口（如 ://external.com），即使你本地有该域名的 Cookie，浏览器也绝对不会发送，同时对方返回的 Set-Cookie 也会被浏览器直接忽略 [1.1, 1.2]。

2. 'include'（跨域强带凭证）

- 含义： 无论同源还是跨域，任何请求都一律强制携带凭证，注意的是后端需要有相应配置，否则会报跨域错误。
- 使用场景： 经典的前后端分离架构，前端页面部署在 A.com，而后端接口服务在 B.com，用户登录状态完全依赖 B.com 的 Cookie。

3. 'omit'（完全拒绝凭证）

- 含义： 彻底谢绝凭证。不管是同源还是跨域，绝对不携带任何 Cookie。
- 使用场景： 请求公共的、无需鉴权的静态资源、公开的三方开放 API（如天气预报、高德地图数据）。使用 'omit' 可以减少请求头体积，提升网络传输效率，同时避免暴露用户的隐私凭证。

## python 中的 self 与 javascript 中的 this 有何不同

1. 本质与保留字

- Python 的 self：不是保留字。它只是一个普通的形参名称，它必须作为类方法的第一个显式参数传入。

- JavaScript 的 this：是保留关键字。不需要作为参数显式定义在函数签名里，JavaScript 引擎会隐式地将其传给函数。

2. 绑定机制（最核心的区别）

- Python 的 self：静态/显式绑，在方法被调用时，由 Python 解释器明确且固定地将当前的类实例绑定给第一个参数 self，它的指向不会因为函数的调用方式改变而漂移。无论你怎么传递这个方法，self 永远指向创建该实例的对象。

- JavaScript 的 this：动态绑定（运行时刻决定），this 的指向完全取决于函数是如何被调用（Invocation Context）的，而不是函数定义在哪里，JS 中经常出现 const self = this; 或 .bind(this) 来“保存上下文”，根据调用方式不同，this 会指向不同的对象：
  - 作为对象方法调用：this 指向该对象。
  - 独立函数调用：在非严格模式下指向全局对象（如浏览器中的 window），严格模式下为 undefined。
  - 构造函数 (new)：指向新创建的实例对象。
  - 箭头函数 (=>)：没有自己的 this，它会词法捕获（继承）外层作用域的 this。
  - call / apply / bind 显式绑定：可以人为强行改变 this 的指向。

3. 是否隐式使用

- Python：在类的方法内部访问实例属性或调用其他方法时，必须显式写出 self.attribute 或 self.method()。如果直接写变量名，Python 会把它当作局部变量或全局变量，而不会去查找实例属性。

- JavaScript：在类的内部（或构造函数中）访问属性或方法时，可以隐式使用，也可以写成 this.property

## v8 是如何执行一段 JS 代码的

V8 引擎通过“解析生成 AST → 解释器生成字节码执行 → 编译器对热点代码进行即时编译（JIT）优化”的流水线机制来执行 JavaScript 代码。

1. 初始化运行环境

在执行代码前，V8 会先准备好基础运行环境，包括：

- 内存空间：创建堆（Heap，存放对象与闭包）和栈（Call Stack，管理函数调用上下文）。
- 全局执行上下文：初始化 window 或 globalThis 等全局对象，以及 Object、Array、setTimeout 等内置 API。
- 事件循环（Event Loop）：启动消息队列机制以支持异步任务调度。

2. 解析阶段（Parsing）：源码 → AST

V8 无法直接理解人类编写的文本代码，需要将其转化为结构化数据：

- 词法分析（Scanner / Lexer）：将源码字符流拆分成一个个不可再分的最小语法单元（Token），例如 var、a、=、1。
- 语法分析（Parser）：根据语法规则将 Token 序列组装成抽象语法树（AST），同时进行语法检查（如果语法错误，此时会直接抛出 SyntaxError）。
- 生成作用域与执行上下文：在此阶段确定变量的作用域（Scope），完成变量提升（Hoisting）和闭包分析。

3. 解释执行阶段（Ignition）：AST → 字节码

早期 V8 直接将 AST 编译成机器码，但这导致内存占用极高。现代 V8 引入了 Ignition 解释器：

- 生成字节码（Bytecode）：Ignition 将 AST 转换为字节码。字节码是介于 AST 和机器码之间的一种抽象指令集，体积远小于机器码，能大幅降低内存消耗并加快页面首次加载速度。
- 逐行解释执行：Ignition 逐条读取字节码并模拟执行，同时在后台收集代码运行时的类型反馈（Type Feedback）（例如记录某个函数的参数一直是整数）。

4. 即时编译与优化（JIT / TurboFan）：字节码 → 机器码

在代码运行过程中，V8 会持续监控各个函数或循环的执行频率：

- 识别热点代码（Hot Code）：如果某段代码被频繁执行（例如循环执行数千次），Ignition 会将其标记为“热点代码”。
- 优化编译（TurboFan / Maglev）：V8 将热点代码的字节码以及之前收集的类型反馈交给优化编译器（如 Maglev 中层编译器和 TurboFan 顶层优化编译器）。编译器会基于假设（例如“变量 x 永远是数字”）直接将其编译成高度优化的底层机器码。
- 直接执行机器码：下次再调用该函数时，CPU 直接执行编译好的机器码，跳过解释步骤，运行速度呈几何级提升。

5. 反优化机制（Deoptimization）

由于 JavaScript 是动态弱类型语言，编译器之前做的类型假设随时可能被打破：

- 触发条件：假设函数 add(a, b) 之前一万次传入的都是数字，TurboFan 已将其优化为数字相加的机器码；但第 10001 次突然传入了字符串 add("hello", "world")。
- 回退过程：优化后的机器码发现类型不匹配，会立即触发反优化（Deopt），废弃当前的机器码，将执行权重新交回给 Ignition 解释器，回退到执行字节码的安全路径上。

6. 性能优化启示

理解 V8 的执行机制后，日常编码中可以通过以下方式迎合引擎优化：

- 保持对象结构稳定：尽量在构造函数中一次性初始化所有属性，不要动态增删属性，以充分利用 V8 的隐藏类（Hidden Class / Map）机制。
- 保持函数参数类型一致：避免同一个函数一会儿接收数字、一会儿接收字符串，防止频繁触发 TurboFan 反优化。

## 现代框架如 React、Vue 相比原生开发有什么优势

核心优势在于以“数据驱动视图”替代繁琐的手动 DOM 操作，并通过组件化架构大幅提升复杂应用的可维护性、开发效率与团队协作能力。

1. 编程范式升级：声明式 UI 替代命令式 DOM 操作

- 原生开发（命令式）：你需要事无巨细地指挥浏览器“先找到某个元素 document.getElementById，再修改它的 innerText，最后切换 classList”。随着交互变复杂，状态与 DOM 极易不同步，产生大量面条式代码。
- 现代框架（声明式）：你只需关注数据状态（State），框架会自动将状态映射为最终的 UI（即 UI = f(State)）。数据一旦改变，视图会自动精准更新，彻底解放开发者手动同步 DOM 的心智负担。

2. 真正的组件化开发与高复用性

- 原生开发：HTML、CSS 和 JS 通常分散在不同文件中，原生 Web Components 封装繁琐且生态较弱，跨页面复用复杂交互模块（如带搜索、分页、排序的表格）十分困难。
- 现代框架：将结构、样式和交互逻辑高内聚地封装在独立的组件（Component）中，组件之间通过清晰的数据流（Props / Events）通信，如同搭积木一样构建大型系统，极易复用与测试。

3. 自动化性能优化与精准更新

- 原生开发：频繁修改 DOM 容易引发浏览器的重排（Reflow）与重绘（Repaint）。如果开发者没有手动做防抖、文档碎片（DocumentFragment）批量更新或节点复用，页面很容易卡顿。
- 现代框架：内置了成熟的更新调度机制（如 React 的 Virtual DOM + Fiber 增量渲染，Vue 3 的细粒度响应式依赖追踪 + 编译时静态标记）。框架会自动合并多次状态变更，计算出最小化的 DOM 差异并批量提交，保证复杂页面依然拥有流畅的帧率。

4. 强大的全栈与跨端生态（一次学习，多端复用）

- 原生开发：代码局限于浏览器环境，若要实现服务端渲染（SSR）、桌面端应用或移动端原生 App，几乎需要完全重写。
- 现代框架：配合 Next.js（React）或 Nuxt（Vue），同一套组件代码可同时运行在服务端与浏览器，轻松解决 SEO 和首屏加载速度问题；借助 React Native、Tauri、Electron 或 Uni-app，一套技术栈即可延伸至 iOS、Android、Windows 和 macOS 客户端。

5. 工程化体系与大规模团队协作规范

- 原生开发：缺乏统一的项目结构约束，10 个人可能写出 10 种截然不同的代码组织方式，项目规模一旦超过几万行，维护成本会呈指数级上升。
- 现代框架：天然融入现代前端工程化工具链（Vite、TypeScript 类型检查、ESLint、自动化单元测试），单向数据流与标准的生命周期/Hooks 规范让大型团队多人并行开发时边界清晰、更易接手。

## SSR 水合是什么

SSR 水合是指在服务端渲染（SSR）中，浏览器接收到服务端预先生成的静态 HTML 页面后，前端 JavaScript 框架（如 React、Vue）接管这些现有的 DOM 节点，为其绑定事件监听器、恢复响应式状态，使其从“只能看不能交互的静态页面”变成“完全可交互的动态单页应用（SPA）”的过程。

### 一、 为什么需要“水合”？（形象理解）

1. 服务端渲染（SSR）—— 抽水制成“干货”：服务端先在后台把组件和数据渲染成纯静态的 HTML 字符串发送给浏览器。此时用户能以最快速度看到首屏内容（首屏加载极快、利于 SEO），但这时的 HTML 就像脱水蔬菜，只有外壳（DOM 结构），没有“水分”（JS 逻辑、事件绑定、响应式状态），点击按钮是没有任何反应的。
2. 客户端水合（Hydration）—— 重新“注水”激活：浏览器下载完前端 JS 脚本后，框架不会粗暴地销毁并重新创建所有 DOM（那样会导致页面闪烁且浪费性能），而是遍历服务端已经渲染好的现成 DOM 树，把对应的 JS 组件实例、状态数据和 onClick 等事件监听器“注入”并关联上去。至此，页面彻底活了过来。

### 二、 水合的完整执行流程

1. 服务端生成 HTML：服务端执行组件代码，拉取数据，生成完整的 HTML 结构并返回给浏览器。
2. 浏览器首次绘制（FCP）：浏览器直接解析并渲染该 HTML，用户立刻看到页面内容（此时处于不可交互状态）。
3. 下载并执行 JS Bundle：浏览器在后台加载前端框架代码与业务 JS 脚本。
4. DOM 节点比对与接管（核心水合阶段）：

- 前端框架在内存中运行组件树，生成虚拟 DOM（Virtual DOM）。
- 框架将虚拟 DOM 与页面上已有的真实 DOM 进行结构比对（不重新创建 DOM 元素，而是直接复用）。
- 为对应的 DOM 节点挂载事件监听器（如点击、输入事件），并初始化组件状态（State / Ref）。

5. 完成交互就绪（TTI）：水合结束，后续所有的页面跳转和状态更新完全接管为纯客户端渲染（CSR）模式。

### 三、 水合过程中的常见问题与挑战

1. 水合不匹配（Hydration Mismatch）

- 原因：服务端渲染出的 HTML 结构或文本，与客户端首次水合时虚拟 DOM 计算出的结果不一致。
- 常见诱因：在组件渲染逻辑中直接使用了 Date.now()、Math.random()，或者直接访问了服务端不存在的 window / localStorage 对象。
- 后果：浏览器控制台会抛出警告（如 React 的 Text content does not match server-rendered HTML），框架为了修正错误可能会被迫丢弃服务端 DOM 并重新客户端渲染，导致性能下降或页面闪烁。

2. 主线程阻塞与“恐怖谷”效应（Uncanny Valley）

- 问题：在大型应用中，水合需要遍历整棵组件树并执行大量 JS 计算，这会长时间占用浏览器主线程。
- 表现：用户明明已经看到了按钮（首屏渲染完成），但因为 JS 正在紧张地进行全量水合，导致点击按钮卡顿或无响应，直到水合彻底结束。

四、 现代框架对水合的演进优化

为了解决传统全量水合带来的性能瓶颈，现代前端框架提出了多种进阶方案：

- 渐进式水合 / 选择性水合（Selective Hydration，如 React 18+）：结合 Suspense，把页面拆分成多个独立区块。优先水合用户正在交互或视野内的核心区域，次要区域延后水合，互不阻塞。
- 岛屿架构（Islands Architecture，如 Astro）：页面默认全部是零 JS 的纯静态 HTML，只针对页面上真正需要交互的局部组件（“孤岛”，如轮播图、购物车按钮）单独进行局部水合。
- 可恢复性（Resumability，如 Qwik）：彻底抛弃传统水合步骤，直接将事件监听器和状态序列化保存在 HTML 属性中，只有当用户真正点击某个按钮时，才按需下载并执行那一小段 JS 代码（实现真正的“零水合开销”）。

## 有没有使用过 async/await，他们的原理是什么

它的本质是 Generator（生成器）函数与 Promise 的语法糖，并内置了一个自动执行器。

1. 协程与状态机（Generator / 底层字节码状态机）：

- 当代码遇到 await 表达式时，当前 async 函数的执行权会被挂起（暂停），并保存当前的执行上下文（包括局部变量和指令指针位置）。
- 主线程（调用栈）不会被阻塞，而是直接跳出该 async 函数，继续执行外部的同步代码。

2. 微任务队列（Promise & Microtask Queue）：

- await 后面的表达式会被强制包装成一个 Promise（即使后面跟的是普通数字或字符串，也会被 Promise.resolve() 包装）。
- 当这个 Promise 状态变为 fulfilled（成功）时，JS 引擎会将恢复 async 函数后续代码的任务推入微任务队列（Microtask Queue）。
- 等到当前同步调用栈清空后，事件循环（Event Loop）取出该微任务，恢复上下文并从上次暂停的 await 处继续往下执行。

## Map 与 WeakMap 有何区别

Map 可以接受任意类型的键并持有强引用，而 WeakMap 只能使用对象（或非全局注册的 Symbol）作为键，且持有弱引用，不会阻止垃圾回收器回收键对象。

Map 的适用场景：

- 需要频繁增删键值对、统计数量（依赖 .size）或遍历所有条目的常规字典存储。
- 键为字符串、数字或布尔值等基础类型的映射表。

WeakMap 的适用场景：

- 关联 DOM 节点元数据：为页面上的 DOM 元素绑定额外状态或事件回调。当该 DOM 元素从页面移除并销毁时，WeakMap 中的关联数据会自动释放，彻底避免内存泄漏。
- 模拟类的私有属性：在早期 JS 或特定封装场景中，以实例 this 作为键存入 WeakMap，实例销毁时私有数据随之自动回收。
- 基于对象的计算结果缓存（Memoization）：缓存某个复杂对象的计算结果，只要该对象还在使用就命中缓存，对象被销毁后缓存自动失效并释放内存。

## 简述 Object.defineProperty

Object.defineProperty() 是 JavaScript 的一个静态方法，用于直接在一个对象上定义一个新属性，或者修改现有属性，并返回该对象。典型应用场景：

- 数据劫持与响应式系统：通过 get 和 set 拦截属性的读取与修改（这也是 Vue 2 实现数据双向绑定的核心原理）。
- 保护对象属性：将 writable 和 configurable 设为 false，防止核心配置或常量被意外篡改或删除。
- 隐藏内部属性：将 enumerable 设为 false，避免内部辅助变量在遍历对象时暴露。

## Object.keys 与 Object.getOwnPropertyNames() 有何区别

Object.keys() 仅返回对象自身所有“可枚举”（enumerable: true）的字符串属性，而 Object.getOwnPropertyNames() 会返回对象自身所有的字符串属性（包括“不可枚举”的属性）。

## 箭头函数和普通函数的区别

普通函数：

- this 指向：动态绑定，取决于函数被调用的方式（如对象调用、全局调用、或通过 call/apply/bind 改变）。
- 作为构造函数 (new)：可以，可以使用 new 实例化对象，拥有自己的 prototype 属性。
- arguments对象：有，函数内部自带类数组对象 arguments 获取实参。
- 生成器函数(yield)：支持，可以使用 function* 和 yield 关键字。

箭头函数：

- this 指向：词法绑定，没有自己的 this，捕获定义时所在外层作用域的 this，且无法被 call/apply/bind 改变。
- 作为构造函数 (new)：不可以，调用 new 会直接抛出 TypeError，且没有 prototype 属性。
- arguments对象：没有，访问 arguments 会向上层作用域查找（或报错），推荐使用剩余参数 ...args 替代。
- 生成器函数(yield)：不支持，不能用作 Generator 函数，内部不能使用 yield。

适用场景建议

- 适合用箭头函数：数组高阶方法回调（map、filter、reduce）、异步回调（Promise.then、setTimeout）以及需要保持外层 this 上下文的闭包场景。
- 适合用普通函数：对象的方法定义、构造函数、需要动态绑定 this 的 DOM 事件处理函数，以及需要使用 yield 的生成器。

## 什么是纯函数

纯函数（Pure Function）是指在相同的输入下，永远会得到相同的输出，并且在执行过程中没有任何可观察的副作用（Side Effects）的函数。

## 在 JS 中如何监听 Object 某个属性值的变化

### Object.defineProperty()

- 监听粒度：单个属性（监听整个对象需递归遍历）
- 新增 / 删除属性：无法监听

- 嵌套深层对象：同样需递归（但可在 get 时按需懒代理，性能更好）
- 操作目标：必须操作 new Proxy() 返回的代理对象

## js 中什么是 AsyncIterable

在 JavaScript 中，AsyncIterable（异步可迭代对象）是一种实现了 [Symbol.asyncIterator] 方法的对象，它允许你使用 for await...of 循环来异步、按需地逐个消费数据。它专门用于处理数据不是一次性就绪，而是随时间推移异步到达的场景（如分页接口请求、文件流读取或 WebSocket 消息）。典型应用场景：

- 流式数据处理：在 Node.js 中逐行读取超大文件（fs.createReadStream），或在浏览器中处理 Fetch API 的流式响应（如逐字输出 AI 大模型的 SSE 流式回复），避免一次性将整个文件读入内存。
- 自动分页拉取：封装需要按页码或游标（Cursor）不断请求下一页的后端 API，让调用方像遍历普通数组一样拉取全量数据。

## 了解什么是 JSBridge 吗

JSBridge（JavaScript Bridge）是连接移动端原生代码（Native，如 iOS 的 Swift/Objective-C 或 Android 的 Java/Kotlin）与网页前端代码（JavaScript）之间的双向通信桥梁。在混合开发（Hybrid App，如微信内置浏览器、支付宝小程序容器或各类 App 内的 WebView 页面）中，网页运行在沙盒环境内，无法直接调用手机的摄像头、GPS、蓝牙、相册或原生支付等底层硬件与系统能力。JSBridge 的核心作用就是打破这层隔离，让前端 JS 可以调用 Native 的原生功能，同时让 Native 也能向网页 JS 推送消息或调用 JS 方法。

## 使用 JS 如何生成一个随机字符串

1. 快捷写法：Math.random().toString(36)（适合非安全场景）

利用 Number.prototype.toString(36) 将随机浮点数转换为 36 进制（包含 0-9 和 a-z），再截取掉前面的 "0."。

-适用场景：生成前端临时 DOM ID、测试数据或非关键唯一标识。
-局限：长度不固定（末尾为 0 时会被省略），只包含小写字母和数字，且 Math.random() 属于伪随机，不可用于密码、验证码或 Token。

2. 自定义字符集与固定长度（适合验证码、短链接）

通过指定字符池（如大小写字母、数字、特殊符号），循环随机抽取指定次数的字符拼接，适用于需要精确控制长度、包含大小写字母，或排除易混淆字符（如去掉 0、O、1、l）的场景。

3. 密码学安全级别：Web Crypto API（适合 Token、密钥、唯一 ID）

- 直接生成标准 UUID（最简单），crypto.randomUUID()，适用于数据库主键、请求追踪 TraceID
- 生成指定长度的高安全随机字符串，crypto.getRandomValues()，适用于鉴权 Token、加密盐值（Salt）、安全验证码

## setTimeout为什么最小只能设置4ms，如何实现一个0ms的setTimeout?

### 为什么会有 4ms 的最小延迟限制？

1. 规范层面的“嵌套钳制”

- 根据 HTML Living Standard 规范：前 4 层（或前 5 次嵌套）的 setTimeout(fn, 0) 实际最小延迟大约为 1ms（受操作系统时钟精度和事件循环调度影响）。
- 一旦定时器内部递归调用自身超过 5 层嵌套，且设定的延迟小于 4ms，浏览器就会强制将最小延迟钳制为 4ms。

2. 保护系统性能与省电

- 早年许多网页动画或轮询脚本使用 setTimeout(fn, 0) 递归执行。如果没有下限限制，CPU 会持续处于 100% 满载状态，导致页面卡死以及移动设备电量迅速耗尽。

3. 后台标签页的进一步限制

- 当网页处于非激活（后台）标签页时，现代浏览器（如 Chrome）为了节能，会将定时器的最小延迟进一步拉长到 1000ms（1秒） 甚至更久。

1. 前端框架的并发渲染与时间切片（如 React Scheduler）

### 如何实现真正“0ms”的宏任务定时器？

要绕过 setTimeout 的 4ms 限制，核心思路是利用浏览器事件循环中其他不受嵌套限制的宏任务（Macrotask）API（注：虽然 Promise.then 和 queueMicrotask 更快，但它们属于微任务，会在当前渲染帧前全部清空，若递归调用会阻塞 UI 渲染，因此不能替代 setTimeout 的让出主线程能力）。

1. MessageChannel（最推荐、性能最好）：MessageChannel 允许创建一个双向通信通道，发送消息产生的回调属于标准的宏任务，不受 4ms 嵌套限制，也不会污染全局 window.onmessage 事件。React 团队的调度器（Scheduler）在实现时间切片（Time Slicing）时正是优先采用此方案。
2. window.postMessage（兼容性备选）：在不支持 MessageChannel 的极老旧环境中，可以通过 window.postMessage 向当前窗口发消息来触发宏任务。

### 使用场景

1. 前端框架的并发渲染与时间切片（如 React Scheduler）

这是 MessageChannel 最著名、最核心的工业级应用场景：

- 痛点：当组件树非常庞大时，一次性同步渲染会长时间占用 JS 主线程（超过 16.6ms），导致页面掉帧、用户点击无响应。
- 为什么不用微任务（Promise）：微任务会在当前帧渲染前全部清空，如果用微任务拆分渲染工作，浏览器依然没有机会去绘制屏幕，页面照样卡死。
- 为什么不用 setTimeout(fn, 0)：如果把一个大任务拆成 20 个小分片，使用 setTimeout 从第 5 个分片开始，每个分片都会被迫白白空等 4ms，仅等待时间就耗掉 60ms+（直接丢掉 3~4 帧）。
- 0ms 宏任务的价值：利用 MessageChannel 在每一帧的空闲间隙内快速执行一小块渲染任务；一旦发现本帧剩余时间耗尽，立即挂起任务把主线程交还给浏览器渲染画面，随后在下一帧以 0ms 延迟无缝恢复执行。

2. 浏览器端海量计算任务分片（防页面假死）

当需要在前端主线程处理大批量数据（例如：解析几十万行的 CSV/JSON 数据、前端导出超大型 Excel、本地图片像素级滤镜处理）且不便引入 Web Worker 时：

- 做法：将大循环拆分为每次只处理 1000 条数据的小批次，每处理完一批，就通过 MessageChannel 派发下一批任务。
- 效果：用户依然可以流畅地滚动页面、点击“取消”按钮或看到实时更新的进度条（如果用 setTimeout 则会因为 4ms 累加导致整体导出时间成倍拉长）。

3. 高频状态变更的异步批量合并（Batching）与后置清理

在编写底层状态管理库、响应式框架或复杂 UI 组件时：

- 异步非阻塞清理：当某些操作需要在当前同步代码及所有微任务（如 Promise、DOM 同步更新）全部彻底结算完毕之后，且在浏览器绘制下一帧之前立即执行收尾工作（例如释放临时缓存、上报一次完整的交互埋点），MessageChannel 能提供最精准、无延迟的“紧随微任务之后的下一个宏任务”时机。

4. 实现 Node.js 风格的 setImmediate Polyfill

- 背景：Node.js 环境中原生提供了 setImmediate(fn)（用于在当前事件循环的 Check 阶段立即执行回调，不受 setTimeout 延迟限制），但现代浏览器标准至今未原生支持 setImmediate。
- 做法：在需要兼容浏览器与 Node.js 的同构（Isomorphic）底层工具库中，开发者通常会使用 MessageChannel 来实现浏览器端的 setImmediate Polyfill，从而保证两端在异步任务调度速度上的一致性。

## return promise 与 return await promise 有何区别

在异步函数（async function）中，return promise 与 return await promise 在正常兑现（resolve）时返回值完全一致，但核心区别在于异常处理（try...catch 能否捕获错误）、finally 代码块的执行时机以及错误调用栈（Stack Trace）的完整性。

## 在 ES6 Class 中，super 的过程中做了什么

在 ES6 Class 中，super 既可以作为函数调用（super()），也可以作为对象引用（super.prop 或 super.method()）。在子类构造函数中调用 super() 的核心作用，是执行父类的构造函数逻辑，完成子类实例对象的内存创建与 this 绑定，并建立起原型链继承。

### 一、 作为函数调用：super() 到底做了什么？（核心机制）

在 ES5 寄生组合式继承中，是先创建子类的 this 对象，再通过 Parent.call(this) 将父类属性挂载到子类实例上；而 ES6 Class 的机制恰好相反——子类的 this 是由父类创建的。
当你在子类 constructor 中执行 super(...args) 时，JS 引擎底层按顺序执行了以下 4 步：

1. 查找并调用父类构造函数

- 通过子类构造函数的内部属性 [[Prototype]]（即 Child.__proto__ === Parent），找到父类构造函数。
- 调用父类的构造逻辑，同时将当前的 new.target（即子类构造函数 Child）传递给父类。

2. 创建实例对象并绑定原型（关键一步）

- 父类根据传入的 new.target（Child），创建一个新的空实例对象，并将该实例的原型链 [[Prototype]] 指向 Child.prototype（这样实例就能访问到子类和父类原型上的所有方法）。
- 如果父类有内置特殊内部槽（如继承自 Array、Error、Map 等内置类），父类会在此阶段分配对应的底层数据结构（这是 ES5 无法原生继承内置类的根本原因）。

3. 初始化父类实例属性

- 父类构造函数中的代码开始执行（如 this.name = name），将父类的实例属性和字段初始化到刚创建的这个实例对象上。

4. 交回 this 控制权给子类

- 父类执行完毕后，将初始化好的实例对象返回，并正式绑定为子类 constructor 中的 this。
- 在此之前（调用 super() 之前），子类的 this 处于未初始化状态（类似暂时性死区），任何访问 this 的操作都会直接抛出 ReferenceError。

### 二、 作为对象引用：super.xxx 做了什么？

在普通方法、静态方法或箭头函数中，将 super 当作对象使用时，它的指向取决于当前所在的上下文环境，但无论在哪种环境下，方法内部的 this 永远指向当前的子类实例（或子类本身）。

1. 在子类普通方法（原型方法）中

- super 指向 Parent.prototype（父类的原型对象）。
- 调用 super.sayHello() 时，相当于执行 Parent.prototype.sayHello.call(this)。
- 注意：由于 super 指向的是原型对象，所以无法通过 super.xxx 读取父类构造函数中定义在实例上的属性（如 this.name），只能访问定义在父类原型上的方法或 getter/setter。

2. 在子类静态方法（static）中

- super 指向 Parent（父类构造函数本身）。
- 调用 super.staticMethod() 时，相当于执行 Parent.staticMethod.call(this)（此时 this 指向子类 Child）。

3. 赋值操作时的特殊行为（super.prop = value）

- 读取 super.prop 时，是从 Parent.prototype（或 Parent）上查找属性；
- 但如果执行赋值操作 super.prop = 123，JS 引擎实际上是将其赋值给当前实例 this.prop = 123（如果父类原型上有同名的 setter，则会触发该 setter 并绑定 this 为当前子类实例）。
